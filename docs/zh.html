Helldivers 2 模組是怎麼運作的

新概念

程式碼：編譯過的機器碼

Arrowhead 的工程師用 C++ 寫遊戲（叫原始碼），再用編譯器翻成 CPU 能直接執行的機器碼。翻譯的過程中，變數名稱、函式名稱、註解全部消失，只剩一串 bytes。因為我們拿到的只有機器碼，所以想知道遊戲在做什麼，就得從機器碼往回推（第 10 章）。

機器碼裝在兩種檔案裡：.exe 是主程式，.dll 是主程式執行時載入的函式庫。Helldivers 2 的分工是：

檔案是什麼
bin/helldivers2.exe引擎：Autodesk Stingray（前身 Bitsquid）。負責畫面、物理、讀檔、執行 Lua 腳本。很多遊戲共用同一套引擎。
bin/game.dll遊戲邏輯：傷害、AI、網路同步，C++ 寫的，而且被加密保護（第 10 章）。
bin/lua51.dllLuaJIT：執行 Lua 腳本的程式（第 2 章）。
data/資源檔：其他所有東西。

你按下「開始遊戲」，Windows 就把 helldivers2.exe 跑起來，變成一個程序，它再把 game.dll、lua51.dll 載入自己裡面。從這一刻起，引擎、遊戲邏輯、腳本都在同一個程序裡執行。

資源：用雜湊找檔案

data/ 裡是一堆名字像 9ba626afa44a3aa3 的封存檔，每個裡面裝著很多資源。引擎要一個資源時，不是用文字名稱找，而是用兩個數字：型別雜湊和名稱雜湊。

雜湊是一個公式：同一段文字永遠算出同一個數字，但不能從數字反推回文字。HD2 用的公式叫 murmur64，算出 64 bit 的數字。例如 Hive Lord 的模型資源叫 content/fac_bugs/cha_hive_lord/cha_hive_lord，雜湊是 0xD465D9C7F77A07CB；型別「lua」的雜湊是 0xA14E8DFA2CD117E2。因為檔案裡只存數字，所以直接打開封存檔看不到任何名稱，要靠別人整理的名稱清單才能翻回來（第 8 章）。

讓模組成為可能的關鍵：patch 檔會蓋過原版

封存檔裡有一種特別的：檔名結尾是 .patch_0、.patch_1…的 patch 檔。引擎讀資源時，如果 patch 檔裡有一個型別和名稱都一樣的資源，就用 patch 檔裡的版本，蓋過原版。這原本是給遊戲更新用的機制。

因為引擎會乖乖讀任何放在 data/ 裡的 patch 檔、而且不檢查內容有沒有被改過，所以任何人都能做一個 patch 檔，把某個資源換成自己的版本。所有 HD2 模組（換造型的、加功能的）都建立在這一點上。

Hive Lord HUD 此時只是一個想法（10/03）：「應該可以做一個 Hive Lord 血條，顯示主血和每塊裝甲的 HP。」遊戲本身不顯示這些，也沒有提供任何「讓你加介面」的功能。所以要做到，得讓我們自己的程式在遊戲裡執行。第一步就是知道：程式要放進 patch 檔，才進得了遊戲。
重點
  1. 遊戲是編譯過的機器碼，原始碼和名稱都不在我們手上。
  2. 資源用「型別 + 名稱」的雜湊來找，檔案裡看不到文字名稱。
  3. patch 檔裡同名的資源會蓋過原版，而且遊戲不檢查，這是模組能存在的根本原因。
自我檢查：為什麼把一個 .dds 貼圖檔直接丟進 data/ 不會有任何效果？

引擎不認得散落的檔案，它只從封存檔裡、用「型別雜湊 + 名稱雜湊」找資源。要讓遊戲用你的貼圖，得把它包進一個 patch 封存檔，並且用跟原版一模一樣的名稱雜湊，才能蓋過原版。

自我檢查：如果遊戲在讀 patch 檔時會檢查數位簽章，模組還能存在嗎？

不能（至少不能用這種方式）。簽章檢查會發現 patch 檔不是官方的而拒絕載入。HD2 沒有做這個檢查，模組才有一扇門。

遊戲迴圈

遊戲不停地重複：讀你的輸入 → 更新世界（怪物移動、子彈飛行）→ 畫出畫面。每重複一次叫一幀，60 FPS 就是每秒 60 幀。所有會「隨時間發生」的事，都發生在這個迴圈裡。

引擎裡的腳本層

Stingray 引擎內建一個 Lua 執行環境，用的是 LuaJIT 版本（語法等於 Lua 5.1）。Lua 是腳本語言：程式以純文字存在，執行時才由 LuaJIT 讀懂並執行，不必事先編譯。引擎原本的設計是讓遊戲邏輯大多寫在 Lua 裡；但 HD2 把幾乎所有邏輯都放進了 C++ 的 game.dll，Lua 只剩一層很薄的「膠水」：

  • 引擎啟動時會載入幾個 Lua 腳本（它們也是 data/ 裡的資源，型別是 lua）。
  • 引擎每一幀會呼叫一個叫 update 的 Lua 函式，還有 render、shutdown 等幾個固定的進入點。
  • 引擎開放了一組 Lua 可以呼叫的功能（例如列出場景裡的物件、在畫面上畫東西），叫 stingray.* API（第 4 章）。

我們量過：遊戲自己的 Lua update 每幀幾乎不花時間（接近 0 ms）。也就是說，遊戲本身幾乎不用這個 Lua 環境，但它一直開著、每幀都在被呼叫。

為什麼這是模組的入口

Lua 的函式存在全域變數裡，而全域變數是可以被改的。因為引擎每幀是「去全域變數 update 裡拿函式來呼叫」，所以只要有人把 update 換成自己的函式，引擎下一幀就會呼叫新的那個：

local original = update          -- 先把遊戲原本的 update 存起來
update = function(...)            -- 換成我們的函式
    do_my_stuff()                 -- 先做自己的事
    return original(...)          -- 再呼叫原本的，遊戲照常運作
end

這種「把一個呼叫導到自己身上，再轉回原本的地方」的做法叫 hook。模組每一幀能做事，靠的就是這五行。

但這裡有一個前提：這段程式本身得先被執行一次，才能把 update 換掉。遊戲只會執行它自己知道的那幾個 Lua 腳本，不會去執行一個陌生的 Lua 資源。誰來執行第一次？這就是下一章的 Loader。

Hive Lord HUD 此時確定了做法：HUD 要用 Lua 寫，搭在 update 上每幀執行。整個 HUD 最後的入口（H.install()）就是本章那五行的加強版：多了錯誤保護（第 4 章）和自我計時。
重點
  1. 引擎內建 Lua，每一幀都會呼叫全域函式 update。
  2. 全域變數可以被改，所以換掉 update 就能每幀執行自己的程式（hook）。
  3. 但要先有人執行你的程式一次，它才有機會去換 update。
自我檢查：如果 hook 時忘了呼叫 original(...)，會發生什麼事？

引擎每幀呼叫的就只剩你的函式，遊戲自己 Lua 層該做的事全部不做了。輕則某些功能失效，重則遊戲壞掉。所以一定要呼叫原本的函式，並把它的回傳值傳回去。

自我檢查：HD2 的遊戲邏輯幾乎都在 C++ 裡，那 Lua 模組還能做什麼？

Lua 層雖然薄，但它在遊戲程序裡、每幀被呼叫，而且能用引擎開放的 API。再加上第 5 章的 FFI，Lua 可以呼叫 Windows 的函式、直接讀遊戲的記憶體，所以能做的事遠超過「遊戲本身用 Lua 做的事」。

關鍵一步：借用一個一定會被執行的原版腳本

把第 1 章和第 2 章接起來就能想到辦法：遊戲啟動時一定會載入某些原版 Lua 腳本，而 patch 檔可以用同名資源蓋過原版。所以只要做一個 patch 檔，裡面放一個跟某個原版腳本同名的 Lua 資源，遊戲就會在啟動時執行我們的版本。

Bingus Shared Loader 選的是 core/wwise/lua/wwise_flow_callbacks：音效系統（Wwise）啟動時一定會載入的回呼腳本。但原版腳本負責音效，被蓋掉了遊戲就沒聲音。所以 Loader 裡面保留了原版腳本的所有功能，再多做「載入模組」這件事。

  • 遊戲的資源放在 data/ 的封存檔裡，用「型別 + 名稱雜湊（murmur64）」定位。Mod 管理器（Arsenal / HD2MM）把模組部署成額外的 9ba626afa44a3aa3.patch_N，裡面同名的資源會蓋過原版。
  • Loader 的封存檔只有一個 lua 資源，名稱雜湊是 0x7251FDD9BB62480A。我們用同一套 murmur64 算過，正好是 core/wwise/lua/wwise_flow_callbacks：遊戲音效系統（Wwise）啟動時會 require 的原版腳本。
  • 所以遊戲一開機載入音效系統，執行的就是 Loader。它裡面保留了原版腳本的所有 Wwise 回呼（wwise_trigger_event、wwise_load_bank…），音效照常運作；README 也特別說明它「保留 Wwise callbacks，不取代 boot」。
  • Loader 本體是編譯過的 LuaJIT bytecode（檔頭 \x1bLJ，約 20 KB）。以下流程是從 bytecode 裡的字串常數、README 和實際 log 整理出來的。

Loader 啟動後做的事

  1. 放大 LuaJIT 的 JIT 快取：所有模組共用遊戲的同一個 LuaJIT，預設快取太小，裝多了會一直被清空（flush）。v18 一開始就調到 16 MB / 8,000 段編譯好的程式（traces），被清空後再長到 64 MB / 16,000 段，並在 log 寫一行 LuaJIT cache:。
  2. 建立共用 log 資料夾 %LOCALAPPDATA%\CowboyBingus\Helldivers2\Logs，開啟 BingusSharedLoader.log。
  3. 建立全域表 CowboyBingusModLoader：放版本、API 等級、模組狀態清單、open_log(檔名)（只接受 ^[%w_-]+%.log$ 這種檔名，避免模組寫到別的路徑）、JIT 快取統計（jit.flushes 等）。
  4. 找到遊戲的 data 資料夾：用 GetModuleFileNameA 取得執行檔路徑，確認結尾是 /bin/helldivers2.exe（不是就停止），推出 /data/。
  5. 掃描所有 patch 檔：FindFirstFileA 列出 9ba626afa44a3aa3.patch_*，逐一打開，檢查封存檔魔數 0xF0000011 和表格，讀每個 lua 資源的開頭，用這個樣式比對第一行： 
    ^%-%- HD2%-Addon: (mods/[A-Za-z0-9_]+/[A-Za-z0-9_/]+)
    bytecode 裡還有一份 murmur64 實作（hasher），看起來會核對宣告的名稱和資源的雜湊是否一致（推測，未在原始碼確認）。
  6. 載入：自動發現的 addon，加上一份內建的 CowboyBingus 模組清單，逐一用 Application.can_get('lua', 名稱) 檢查是否存在：不存在記 not installed；存在就 pcall(require, 名稱)，成功記 loaded，失敗記 load failed: 原因。

為什麼要有一個「共用」的 Loader

同一個資源只能有一個 patch 勝出。如果每個模組都自己去蓋 wwise_flow_callbacks，就只有最後一個會生效，其他全部消失。所以社群用一個共用的 Loader 佔住這個入口，再由它依序載入所有模組。你的模組不需要蓋掉任何原版資源，只要放一個新名稱的 Lua 資源，第一行寫上 -- HD2-Addon: … 讓 Loader 找得到。

模組管理器（Arsenal、HD2MM）負責把每個模組寫成 data/ 裡的一個 patch 檔。它每次部署都會重新分配 patch 編號，所以你不能假設自己的模組固定在某個編號（第 14 章會再遇到這件事）。

模組怎麼配合 Loader

用途做法
讓 Loader 找到我們原始碼第一行寫 -- HD2-Addon: mods/hivelordhud/hive_lord_hud。build_hive_lord.py 打包時檢查這一行，並把它改成正確的資源名。
打包格式每個 Arsenal 選項一個 patch 檔，裡面一個 lua 資源：名稱雜湊 = murmur64(資源名)，內容 = (長度, 2 = 純文字) + 原始碼。必須是明文、無 BOM（BOM：有些編輯器會在檔案開頭偷偷加上的 3 個 bytes）：編譯成 bytecode 會丟掉第一行註解，Loader 就找不到。
開始執行被 require 時，檔案最上層只跑一次：先用全域變數擋重複載入（HD2HiveLordHud / HD2HiveLordPlateFix），再把自己包在全域 update() 外面。之後每幀的工作都在包裝函式裡，跟 Loader 就沒有關係了。
寫 logCowboyBingusModLoader.open_log('HiveLordHud_<時間>.log')，log 和其他 Bingus 模組放在同一個資料夾。沒有 Loader 時退回 %TEMP%。
設定選單Mod Options Menu 也是一個透過 Loader 載入的模組（Megapack 內附），提供全域的 ModOptionsMenu。HUD 在 update 裡才去找它，因為載入順序不保證它比我們早。
除錯模組沒反應時，第一步看 BingusSharedLoader.log：有沒有出現、是 loaded 還是 load failed。

沒有 Loader 還能用嗎？

不能。我們的模組只是一個叫 mods/hivelordhud/hive_lord_hud 的 lua 資源，遊戲本身沒有任何地方會 require 這個名字。沒有 Loader，資源會被部署進遊戲資料夾，但永遠不會被執行：不會報錯，也不會有任何效果。

  • 程式裡唯一對「沒有 Loader」做的備援，是 log 檔改寫到 %TEMP%。但前提還是模組有被載入，所以實際上用不到。
  • 設定選單也會一起消失：Mod Options Menu 本身就是靠 Loader 載入的模組。
  • 理論上可以學 Loader，自己換掉一個原版腳本當入口。但同一個資源只能有一個 patch 勝出，這樣會跟 Loader 和其他模組互相覆蓋，還得自己維護原版腳本的功能，所以不這樣做。這也是 Loader 存在的意義：讓所有模組共用一個入口，不必搶同一個原版腳本。

所以安裝說明把 Bingus Shared Loader 列為必要的相依模組；Mod Options Menu（Megapack）則是選配，沒有它 HUD 會用預設值執行。

容易踩的坑
  • 遊戲是 LuaJIT（Lua 5.1 語法）。// 整除、string.pack、math.type 這類 Lua 5.3 以後才有的東西都不能用；離線測試要用 LuaJIT 版的 lupa（在 Python 裡執行 Lua 的套件），否則測試會通過、進遊戲才 load failed。
  • 所有模組共用同一個 Lua VM 和同一份 FFI 宣告：ffi.cdef 要包 pcall（別的模組可能先宣告過），全域變數名稱要獨特。
  • Arsenal 裡 Loader 要放在清單最下面（預設優先順序），換了順序要 Purge + Deploy。
  • Loader 綁定遊戲版本。遊戲大更新後要等 Loader 更新。
Hive Lord HUD 此時的前 69 個版本，其實是跟我們自己寫的研究用偵察模組 Recon 打包在同一個模組裡（這個工具沒有公開，第 9 章會介紹它的原理），由 Loader 載入。到 v70 才獨立出來，有了自己的資源名稱 mods/hivelordhud/hive_lord_hud。之後的 Dead Plate Fix 則是第二個資源 mods/hivelordhud/plate_fix，在 Arsenal 裡是另一個可以單獨勾選的選項。
重點
  1. Loader 用 patch 檔蓋掉一個「遊戲啟動一定會載入」的原版腳本，並保留它原本的功能。
  2. Loader 再掃描所有 patch 檔，用第一行 -- HD2-Addon: 找出模組，逐一 require。
  3. 共用一個入口，所有模組才不會互相蓋掉。
自我檢查：如果你把模組的 Lua 編譯成 bytecode 再打包，會發生什麼事？

Loader 認不出它：bytecode 會丟掉註解，第一行的 -- HD2-Addon: 就不見了。模組會被部署進遊戲，但永遠不會被執行，也不會出現在 Loader 的 log 裡。

自我檢查：模組「沒反應」時，第一個該看哪個檔案？為什麼？

BingusSharedLoader.log。它記錄了每個模組有沒有被找到、是 loaded 還是 load failed: 原因。如果你的模組根本不在清單上，問題出在打包或部署；如果是 load failed，問題出在程式本身。

新概念

world、unit、骨頭
場景；場景裡的物件；模型骨架的節點。

Gui、保留模式

pcall、assert
Lua 攔住錯誤的呼叫；引擎內部的自我檢查，失敗就直接結束遊戲。

引擎給了什麼

引擎把一部分功能開放給 Lua，叫 API。模組最常用的是這幾組：

  • Application：整個遊戲，例如 Application.worlds() 列出目前所有的 world（場景：船上、任務、選單各是一個）。
  • World / Unit：World.units(world) 列出場景裡所有的 unit（一隻怪、一個玩家、一台攝影機都是 unit）。Unit.resource_name(u) 告訴你它用的是哪個模型資源（回傳雜湊）。Unit.node(u, 'head') 找到名叫 head 的骨頭，再讀它的位置。
  • Camera：Camera.world_to_screen 把 3D 位置換成螢幕上的座標。
  • Gui：在畫面上畫矩形、文字、三角形。

要注意：腳本拿到的 unit 只是一個 handle（號碼牌），不是指向資料的位置。你可以拿它去問引擎問題，但不能從它直接走到怪物的血量資料。引擎也沒有開放「讀某個怪物的血量」這種 API。這件事決定了 HUD 後面的路（第 5 章）。

例子：HUD 怎麼找到 Hive Lord

  • 每 2 秒掃一次 Application.worlds() 裡每個 world 的 World.units()，比對 Unit.resource_name。發行版回傳的是雜湊過的 IdString64，所以比對路徑字串 hive_lord 或雜湊 d465d9c7f77a07cb（= murmur64 of content/fac_bugs/cha_hive_lord/cha_hive_lord）。
  • 剛出現的 world 要等 10 秒穩定才碰。main_world() 大約每 3 秒就換一次，不能拿來判斷。
  • HUD 畫在「單位最少的那個穩定 world」上（UI world；遊戲 world 有上千個單位）。world 一旦消失，它的 Gui 也跟著消失：只遺忘，絕不再呼叫 destroy。
  • 單位值是 handle 不是指標，無法從單位直接走到元件記憶體，所以血量要另外找（下一節）。
  • Hive Lord 死後 2.5 秒淡出、再 1.5 秒就完全不再碰那具屍體，並記下它的位址，之後掃描直接跳過。這是為了避開一個會讓遊戲當掉的情況（見「踩過的坑」）。

畫面：保留模式的 Gui

引擎的 Gui 是保留模式：Gui.rect(...) 建立一個矩形，拿到一個編號；之後用 Gui.update_rect(編號, ...) 改它的位置、大小、顏色；不用了要銷毀。它不是每幀把畫面清空重畫。

  • 每個群組 0.35–0.6 秒淡入淡出，淡出完才銷毀。
  • 圖元只有在顏色、大小、位置或文字改變時才送進 Gui；建立的那一幀不送更新（同一幀建立又更新的文字在遊戲裡不會出現）。
  • 參數必須是真正的引擎物件：Vector3(x, y, layer)、Vector2(w, h)、Color(a, r, g, b)。
  • Low-poly 面板的每個面是一個真正的 Gui.triangle。它的點要寫成 Vector3(x, 0, y)（從 helldivers2.exe 反組譯確認：y 和 z 會互換）。如果建立三角形失敗，會自動退回用 2 px 的矩形條拼。
  • 字型用基礎封存檔裡就有的 core/performance_hud/debug；粗體是同一段文字往右疊 1 px 的副本。

做錯會怎樣：兩種錯誤

  • Lua 層的錯誤（例如對 nil 做加法）：可以用 pcall 攔住。所以模組的每幀工作都包在 pcall 裡，出錯就永久關閉自己，遊戲照常。
  • 引擎內部的錯誤：引擎每個 API 裡面都有自我檢查（assert），參數不對、對象已經不存在，就直接結束整個遊戲。pcall 攔不住，因為錯誤根本沒有回到 Lua。

因為第二種錯誤無法挽救，所以模組必須在呼叫之前就確認不會出錯：world 還在不在、unit 還活著沒、參數格式對不對。這些規則幾乎都是當掉之後才學到的（見下面）。

Hive Lord HUD 此時連續當掉了好幾次，每次都教了一條規則：
  • v0：每個 tick 都呼叫 Gui.rect 建立新矩形、從不銷毀，每秒累積約 2,400 個，遊戲 1 分鐘和 3.5 分鐘後硬當。改成保留模式的正確用法。
  • v27：用遊戲的原生字型畫字，第一次繪製就當掉，還留下關不掉的遊戲程序，只能重開機。從此只用基礎資源裡的除錯字型。
  • v42–v64：玩家死亡、Hive Lord 死後屍體被移除時，還在對已經消失的 unit 呼叫 API。改成每次呼叫前先 Unit.alive(u)，Hive Lord 死後完全不再碰它。
  • v40：Unit.world_position(u, 0) 對所有單位都回傳原點，距離永遠是 0 m。改用具名骨頭（head、root）。
重點
  1. 引擎 API 讓模組能看場景、找物件、畫畫面，但沒開放的事（例如讀血量）就做不到。
  2. Lua 錯誤可以攔，引擎內部的錯誤會直接結束遊戲，所以要「呼叫前先確認」。
  3. Gui 是保留模式：建立一次、之後修改、記得銷毀。
自我檢查：為什麼模組已經包了 pcall，HUD 還是會讓遊戲當掉？

當掉的原因在引擎內部（assert 失敗、存取已經不存在的物件），錯誤沒有回到 Lua，pcall 根本沒機會攔。唯一的辦法是不讓這種呼叫發生。

自我檢查：HUD 能用 World.units 找到 Hive Lord，為什麼還讀不到它的血量？

拿到的只是一個 handle，不是資料的位置；引擎也沒有開放讀血量的 API。血量存在 game.dll 管理的記憶體裡，要用第 5 章的方法自己去讀。

FFI 是什麼

LuaJIT 有一個標準 Lua 沒有的功能：FFI（Foreign Function Interface）。它讓 Lua 直接呼叫 C 語言寫的函式，包括 Windows API，也能直接配置、讀寫一塊記憶體。遊戲帶的 lua51.dll 沒有把這個功能關掉。

local ffi = require('ffi')
pcall(ffi.cdef, 'int QueryPerformanceCounter(int64_t* counter);')  -- 告訴 FFI 函式長什麼樣
local kernel32 = ffi.load('kernel32')                               -- 載入函式所在的 dll
local buf = ffi.new('int64_t[1]')                                   -- 配置一塊 C 記憶體
kernel32.QueryPerformanceCounter(buf)                               -- 呼叫 Windows API
print(tonumber(buf[0]))                                             -- 高精度計時器的值

有了 FFI，模組能做的事一下子變成「一般 Windows 程式能做的事」：

  • 例如呼叫 Windows 的執行緒 API，決定遊戲的每條執行緒跑在哪顆 CPU 核心。
  • HUD 用它呼叫 ReadProcessMemory，讀遊戲程序自己的記憶體。

為什麼 FFI 也很危險

  • 沒有安全網：函式宣告錯、參數給錯、讀了不該讀的位址，遊戲直接當掉，pcall 攔不住（原因在第 6 章）。
  • 所有模組共用一個 Lua 環境：ffi.cdef 重複宣告會出錯，所以每個宣告都包 pcall；ffi.load 拿到的物件要一直留著，否則 dll 可能被卸載、函式失效。
  • 能力等於一般程式：一個惡意的 Lua 模組也能讀你的檔案、連網路。這是第 16 章「只裝可信模組」的原因。
Hive Lord HUD 此時確定了「讀血量」只能走 FFI：用 ReadProcessMemory 讀遊戲記憶體。但問題馬上變成兩個：血量在記憶體的哪裡？那裡的資料長什麼樣子？要回答，得先懂記憶體（第 6 章）和遊戲怎麼組織資料（第 7 章）。
重點
  1. FFI 讓 Lua 呼叫 Windows API、直接操作記憶體，是模組能做「引擎沒開放的事」的關鍵。
  2. 它沒有安全網，錯了遊戲直接當掉。
  3. 模組的能力因此等於一般程式，這同時是力量也是風險。
自我檢查：如果遊戲帶的 LuaJIT 把 FFI 關掉了，HUD 還做得出來嗎？

血條和面板做不出來：引擎沒有讀血量的 API，只能靠 FFI 讀記憶體。標記、出土警告這類只用引擎 API 的部分還可以。

一個數字在記憶體裡的樣子

記憶體是一長排格子，每格 1 byte（0–255），每格有一個編號叫位址。位址和內容習慣用十六進位寫（0x 開頭，每位 0–9、A–F）。血量這種整數通常用 4 bytes 存，叫 int32；而且「低位在前」，所以 150,000 = 0x000249F0 在記憶體裡是 F0 49 02 00：

每個程序有自己的一套位址

程式看到的位址不是 RAM 條上的實際位置。Windows 給每個程序一套自己的虛擬記憶體，以 4 KB 的分頁為單位，對應到實體 RAM（或暫時放在 SSD 上）。

這帶來三個對模組很重要的結果：

  1. 外部程式碰不到遊戲的記憶體：同一個位址在兩個程序裡是不同的 RAM。外部程式要讀遊戲，必須先向 Windows 申請遊戲的 handle（OpenProcess），再請 Windows 代讀。反作弊就在這一步攔截（第 16 章）。但模組在遊戲程序裡面，用的是遊戲自己的位址，不需要經過這一步。
  2. 讀錯位址會當掉：如果某個位址沒有對應任何分頁，或分頁不允許讀，CPU 會觸發存取違規，程式立刻結束。這就是第 5 章說 FFI「沒有安全網」的原因。
  3. 程式碼不能直接改：程式碼所在的分頁標記為「可讀、可執行、不可寫」，要改得先呼叫 VirtualProtect 改權限。
延伸：RAM 本身與快取

RAM 是 CPU 的工作桌，速度比 SSD 快約 1,000 倍，但比 CPU 內建的快取慢很多：

層級大小（你的 i9-13900H，約略）拿一筆資料要多久（約略）誰管
暫存器每個核心十幾個 64 位元格子不到 1 奈秒編譯器（就是組合語言裡的 rax、rcx）
L1 快取每個 P 核心 48 KB 資料約 1 奈秒CPU 自動
L2 快取每個 P 核心 1.25 MB約 4 奈秒CPU 自動
L3 快取全部核心共用 24 MB約 10–20 奈秒CPU 自動
RAM16 GB約 80–100 奈秒作業系統分配
SSD（分頁檔）數百 GB約 50–100 微秒（比 RAM 慢約 1,000 倍）作業系統搬進搬出

例如一台只插了一條 16 GB RAM（單通道）的筆電，遊戲在船上就可能用到 4.7–6.4 GB，系統剩下的可用 RAM 常常不到 1 GB。RAM 不夠時，Windows 會把較少用的分頁搬去 SSD，遊戲用到時要等 SSD 讀回來，就會頓幀。

一個程序裡的三種區域

  • 程式碼區：dll 的機器碼，執行中不變。
  • 資料區：dll 裡固定位置的變數（全域變數），整場遊戲都在同一個地方。
  • 堆積：遊戲執行中才配置的資料，例如每隻怪的血量。位置每場都不同，還可能被遊戲搬家。

還有兩件事讓「找到血量」變難：

  • ASLR：Windows 每次啟動都把 dll 放在不同的位址（防止攻擊）。所以不能記「血量在 0x7FFF…」這種絕對位址，只能記「從 dll 開頭算起第幾個 byte」，叫 RVA。實際位址 = 這次的基址 + RVA。
  • 指標：堆積上的資料位置不固定，但資料區裡的全域變數會存著它的位址。這種「存著位址的值」叫指標。從固定的全域變數出發，沿著指標一路找下去，就能找到每場位置都不同的資料。
（預設值是 10/02 那次 game.dll 的 update 函式指標所在位置）
Hive Lord HUD 此時知道了目標：Hive Lord 的血量是一個 int32，放在遊戲程序的堆積上某處，位置每場都不同。要穩定找到它，需要一個固定的起點（game.dll 資料區的某個全域變數，以 RVA 記住），再沿著指標找下去。但要知道「指標指到的那一大塊資料裡，哪 4 bytes 才是主血」，得懂遊戲怎麼組織資料（第 7 章）。
重點
  1. 數字在記憶體裡就是幾個 bytes，int32 是 4 bytes、低位在前。
  2. 每個程序有自己的虛擬記憶體；外部程式要讀得經過 Windows，模組在裡面則不用。
  3. 讀錯位址會當掉；dll 位置每次不同，所以記 RVA、從全域變數沿指標找。
自我檢查：今天 game.dll 載入在 0x7FFFB5F70000，一個全域變數的 RVA 是 0x3326688，它的實際位址是多少？明天呢？

今天是 0x7FFFB5F70000 + 0x3326688 = 0x7FFFB9296688。明天基址會不同，但 RVA 一樣是 0x3326688，用明天的基址加上去就好。這就是只記 RVA 的原因。

自我檢查：為什麼不能直接在程式裡寫死「血量在 0x29A60000A64」？

血量在堆積上，位置每場、甚至每次被遊戲搬家時都會變。寫死的位址下次就指到別的東西或根本不存在，讀了會讀到錯的資料，或觸發存取違規直接當掉。

結構與位移

C++ 用 結構（struct）把相關的資料綁在一起。編譯後名字消失，只剩「這個欄位從開頭算起第幾個 byte」，叫位移。很多筆同樣的結構一筆接一筆排成陣列，每筆大小叫跨距，第 n 筆在「開頭 + n × 跨距」。

開發者寫的 C++（我們看不到，這是推測的樣子）
struct HealthRecord {        // 一隻怪的血量紀錄
    // ...
    int32_t main_hp;         // 主血
    // ...
    int32_t armor[39];       // 每區裝甲
    int32_t zone_hp[38];     // 每區 HP
    int32_t end_marker;      // 0xFFFF
};

HealthRecord* records;       // 很多筆連在一起
records[6].main_hp -= 500;   // 第 6 隻扣 500 血
編譯後在記憶體裡只剩位移
// 每筆紀錄 0x1B8 = 440 bytes，一筆接一筆
// 第 n 筆在：records + n × 0x1B8

+0x014  主血          (4 bytes)
+0x05C  裝甲 × 39     (每個 4 bytes)
+0x0F8  區域 HP × 38  (每個 4 bytes)
+0x190  0xFFFF 標記

// 所以「第 6 隻的主血」=
//   records + 6 × 0x1B8 + 0x14
// 我們的模組就是照這個公式去讀

遊戲怎麼管理怪物：ECS

HD2 用一種叫 ECS 的架構：場上每個東西只是一個實體編號（例如某隻 Hive Lord 是 0x22A）；資料一包一包掛在編號上，叫元件（血量元件、模型元件…）；同一種元件由一個系統集中管理。健康系統把所有怪的血量紀錄放在一個大陣列裡。

健康系統要從「實體編號」找到「陣列裡第幾筆」，用的是雜湊表：一張固定大小的表，每格放 {實體編號, 第幾筆}。用編號算出一個起始格，是就讀出來，不是就往下一格找。

設計數值與執行中數值

「Hive Lord 最大血量 150,000、每塊板子 15,000、裝甲值 5」這些是設計數值，寫在 data/ 的遊戲資料表裡，遊戲沒開也讀得到（第 8 章）。「這隻 Hive Lord 現在剩 118,350」是執行中數值，只在記憶體的那筆紀錄裡。

這個區分很有用：設計數值可以變成指紋。例如 Hive Lord 那 39 個裝甲值（預設區 5，然後 6、10、5、5…）在戰鬥中永遠不變，而且組合很獨特。所以在記憶體裡看到一筆紀錄的裝甲欄位剛好是這 39 個數字，就幾乎可以確定它是 Hive Lord 的紀錄。

重點
  1. 編譯後只剩位移：「紀錄 +0x14 是主血」就是全部的資訊。
  2. 遊戲用系統集中管理同一種資料，用雜湊表從實體編號查到第幾筆。

R + 6 × 0x1B8 + 0x14 = R + 0xA50 + 0x14 = R + 0xA64。

自我檢查：為什麼用「裝甲值」而不是「血量」當指紋？

血量在戰鬥中一直變，下一幀就對不上了；裝甲值從頭到尾不變，又是 39 個數字的獨特組合，不容易跟別的東西撞在一起。HUD 早期用「主血 = 150000」當錨點，結果 Hive Lord 一受傷就找不到了（v9 的失敗）。

FileDiver 怎麼運作

遊戲的資源怎麼存

  • data/ 資料夾裡是一堆用 16 位十六進位命名的封存檔，每個封存檔分成三個檔案：主檔、.stream（串流資料，例如音效）、.gpu_resources（貼圖、模型頂點）。
  • 主檔的格式：標頭（魔數 0xF0000011、型別數、檔案數）→ 型別表 → 檔案表（每個檔案的名稱雜湊、型別雜湊、在三個檔案中的位移和大小）→ 資料。我們自己打包模組用的 patch 檔就是同一個格式。
  • 檔案名稱只存 murmur64 雜湊，不存字串。FileDiver 附了約 25 萬行的已知名稱清單（hashes/），把雜湊翻回可讀的路徑；查不到的就只能顯示雜湊。Hive Lord 的區域名稱就是我們自己暴力破解 32-bit 雜湊（murmur64 的高 32 位元）找回來的。
  • FileDiver 開啟 data/ 時讀過所有封存檔的表格，建立「(名稱, 型別) → 位置」的索引；後面的 patch 會蓋過前面的同名檔案，跟遊戲的行為一樣。

它能匯出什麼

模型（glTF / glb 這兩種通用 3D 檔案格式，含骨架和動畫）、貼圖（png）、Wwise 音效（ogg / wav）、文字表（JSON）、動畫狀態機、prefab（預先組好的物件組合）等。我們用到的是：

  • Hive Lord 模型：filediver.exe -g <遊戲資料夾> -i content/fac_bugs/cha_hive_lord/cha_hive_lord.unit --model-format glb。從骨架和碰撞節點的名稱與位置，確認了 spine0 在尾端、每塊板子對應哪根骨頭、尾巴上方那塊板子不屬於任何區域。
  • 動畫狀態機（sm-state-dumper）：出土警告用的位置層、動作層狀態名稱。

遊戲資料表（datalib）

  • 遊戲玩法的數值（每種敵人的元件：血量、裝甲、武器、爆炸…）存在 datalib 二進位資料塊裡（generated_entities.dl_bin 等），另有一份型別庫 dl_library.dl_typelib，描述每個結構的欄位名稱、型別、位移和大小。FileDiver 的原始碼內附這些資料塊和對應的 Go 結構。
  • 坑：FileDiver 手寫的 Go 結構會隨遊戲更新而過時。HealthComponent 實際是 22,096 bytes、51 個欄位，用舊結構讀出來是亂碼。所以我們改成直接從型別庫讀目前的欄位位移；另一個坑是每個資料塊前面的標頭（DLInstance header）是 28 bytes，不是 24，讀錯 4 bytes 後面就全部錯位。

Recon 怎麼運作

GameGuard 會擋外部的除錯器和記憶體讀取工具，所以沒辦法用 Cheat Engine、x64dbg 這類工具直接看遊戲。Recon 的做法是把「偵察」本身做成一個模組：它在遊戲裡面執行，用 LuaJIT FFI 讀自己程序的記憶體，把結果寫進 log。

使用循環

  1. 把這次要查的指令寫進 %TEMP%\HD2Recon_cmd.lua（一般的 Lua，例如 R.scan('48 8B ?? 20')）。
  2. 啟動遊戲。Recon 被 Loader 載入後，先自動把 game.dll 和 helldivers2.exe 的基址、大小、各區段寫進 log（R.about）。
  3. 接著讀取指令檔，用 loadstring 編譯、setfenv 給它一個能呼叫 R.* 的環境，包在 pcall 裡執行。出錯只會寫一行 run error，不影響遊戲。
  4. 關遊戲、讀 log，決定下一輪要查什麼。每次重開遊戲就會重跑一次指令檔。

R.dump / R.savehex dump 一段記憶體到 log，或存成二進位檔。Hive Lord 血量紀錄的格式就是從這種 dump 推出來的。

R.ldld_census掃描整個程序的記憶體，找遊戲資料表區塊（以 LDLD 開頭），再用 FileDiver 的型別名稱清單對出是哪種表。實測 4.7 GiB 約 23 秒、587 個區塊，24 種型別對出 23 種。
R.dump_module把已經在記憶體中解殼的 game.dll（約 71 MiB）整個寫成檔案。硬碟上的 game.dll 是加密的，這份 dump 才是能反組譯的版本，後面所有靜態逆向（Ghidra、capstone）都靠它。
R.hook_update / R.on_tick實驗性。game.dll 的 get_plugin_api 會把 11 個回呼函式指標寫進 .data 的一個結構，其中一個是每次模擬 tick 呼叫的 update(dt)。這個功能把那個指標換成自己的 Lua 函式（先確認槽位裡的值等於預期才換，並一定會呼叫原本的函式），量到遊戲模擬約 63 Hz。這是 Recon 唯一會寫入的地方，寫的是資料區的一個指標，不是程式碼。早期 HUD（v0–v2）用它驅動，之後改成包裝全域 update()。

安全上，每次讀取前都先用 VirtualQuery 確認那段記憶體已配置、可讀、不是 guard page，從不呼叫 VirtualProtect，也從不修改程式碼。

它在這個專案裡的角色：HUD 前 69 個版本是跟 Recon 打包在一起發佈的（共用它的 log 和 tick），v70 才獨立成 Hive Lord HUD。HP 紀錄的第一次 dump 和 game.dll 的解殼 dump 都是 Recon 做的；健康系統和可見性遮罩系統的位置，則是從那份解殼 dump 靜態分析出來的。

Hive Lord HUD 此時（10/03，v7–v10）用 Recon 的做法找到了血量紀錄：
  • v7：在堆積裡分時搜尋 [150000, 150000, 15000×6] 這種數字序列（前兩個部位、加上板子的設計 HP）。
  • v8：找到後把附近的記憶體 dump 出來，對照 FileDiver 的設計數值，推出紀錄格式：主血在 −0xE4、裝甲在 −0x9C、部位 HP 從 0 開始（相對於部位陣列），結尾 0xFFFF。
  • v9 失敗、v10 修正：用「主血 = 150000」當錨點，Hive Lord 一受傷就找不到；改用不會變的裝甲值當指紋。
這個「搜尋堆積」的方法能用，但有一個藏得很深的問題（第 11 章）。
重點
  1. 在反作弊下觀察遊戲的辦法，是把觀察工具做成模組，在遊戲裡面讀。
  2. 用指令檔遙控要查什麼，結果寫 log，每次重開遊戲跑一輪。
  3. dump 出來的記憶體，加上 FileDiver 的設計數值，就能推出資料的格式。
自我檢查：Recon 和 Cheat Engine 都是讀遊戲記憶體，為什麼一個會被反作弊擋、一個不會？

Cheat Engine 是外部程式，要先跟 Windows 申請遊戲的 handle，反作弊的驅動就在這一步攔截。Recon 在遊戲程序裡面，讀的是自己的記憶體，不需要申請 handle。

逆向工程是在沒有原始碼的情況下，從程式的行為和機器碼推出它在做什麼。本文用到兩種方式：

靜態分析

不執行程式，直接讀 dump 出來的機器碼。用反組譯器轉成組合語言，再找：某個位移被誰用到、某個全域變數被誰讀、某個函式被誰呼叫（叫交叉引用，xref）。

動態分析

在程式執行時觀察：讀某段記憶體、看數值怎麼變、記錄函式被呼叫了幾次。因為反作弊會擋外部的除錯器，我們把觀察工具做成模組（Recon）。

  • 特徵碼（AOB，array of bytes）：一串 bytes 的樣式，可以含萬用字元，例如 48 8B ?? 20，用來在記憶體裡找特定的程式碼。
  • 指紋：一組不會變、又夠獨特的值，用來確認「找到的真的是我要的東西」。例如 Hive Lord 39 個部位的裝甲值，在戰鬥中永遠不變。

為什麼要 dump：加殼

game.dll 被 Themida 加殼：硬碟上的檔案是加密的，載入時才在記憶體裡解開。所以直接拿硬碟上的 game.dll 去反組譯只會得到亂碼，要用 Recon 的 dump_module，把記憶體裡已經解開的 game.dll 整個存下來（約 71 MiB），再拿去分析。

組合語言入門

反組譯器（capstone、Ghidra）把機器碼轉成組合語言：一行一個很小的動作。例如 C++ 的一行：

C++
hp = std::min(hp, -1);   // 血量最多 -1
組合語言（真的出現在 game.dll）
mov   eax, [r9+rdx*4+0xf8]  ; 從記憶體讀 hp
mov   ecx, 0xffffffff       ; ecx = -1
cmp   eax, ecx              ; 比較
cmovl ecx, eax              ; 較小的留在 ecx
mov   [r9+rdx*4+0xf8], ecx  ; 寫回記憶體
  • 暫存器：rax、rcx、r9…是 CPU 內建的小格子，計算前要先把資料搬進來。
  • 方括號 [ … ] = 去這個位址讀寫記憶體。[r9+rdx*4+0xf8] = 「紀錄開頭 + 第幾區 × 4 + 0xF8」，剛好就是第 7 章的位移。
  • 全域變數：mov rdi, [rip + 0x2aa2ec6] = 讀「下一條指令的位址 + 0x2aa2ec6」那裡存的值。把位移算出來，就得到全域變數的 RVA。
  • 函式參數：前 4 個放在 rcx、rdx、r8、r9；call 是呼叫函式；cmp + je/jne 是比較和跳躍（等於 if）。

找到固定起點的過程

四個步驟

  1. 先從遊戲資料知道要找什麼值。FileDiver 解出 Hive Lord 的 HealthComponent：主血 150,000、每塊板子 15,000、39 個固定的裝甲值（5, 6, 10, 5…）。這組數字就是在記憶體裡認出它的指紋。
  2. 在遊戲中搜尋，找到那筆紀錄。單位是 handle，不能順著指標走到元件，所以早期版本（v7–v10）分時掃描整個堆積，找這組數字。找到後把前後的 bytes dump 出來，對照戰鬥中哪些值在變，推出紀錄格式：主血 +0x14、裝甲 +0x5C、38 區 HP +0xF8、結尾標記 0xFFFF，一筆 0x1B8 bytes。
  3. 反過來從程式碼找出管理這些紀錄的全域變數。
    • 用 Recon addon 把已經在記憶體中解殼的 game.dll 整個 dump 出來（硬碟上的檔案被 Themida 加密）。
    • 用 Python + capstone 掃整個程式碼，找出用到這些偏移量的指令（0x1B8 的跨距、+0xF8、+0x14），找到傷害函式 0x9235F0 等血量相關函式。
    • 這幾個函式全部從同一個位置 [rip + X] 載入系統指標，換算出來就是 game.dll + 0x3326688。再看函式怎麼查表，得出 key 表、容量、紀錄陣列的偏移。
    • 可見性遮罩系統 +0x3326708 的找法一樣：從 gore 函式 0x903C70 追到遮罩設定函式 0x721D20，它們也從一個全域變數載入系統指標；entry 的格式（applied / override / touched / base）是讀設定函式和更新函式 0x721680 的程式碼推出來的。
  4. 實際使用與驗證。程式裡存的是相對位移（RVA），執行時用 GetModuleHandleA('game.dll') + RVA 算出實際位址。每次讀取都重新檢查指紋，不符就跳過。遊戲中的 log 確認過兩者都正確：v83 一次就找到紀錄，Plate Fix v3 寫入後板子在 0.1 秒內隱藏。

對應的程式（hive_lord_plate_fix.lua，節錄）：

local HEALTH_RVA, VIS_RVA = 0x3326688, 0x3326708

local function table_header(base_rva, keys_off, cap_off)
    local base = M.game_base()                -- GetModuleHandleA('game.dll')
    if not base then return nil end
    local S = ptr(base + base_rva)            -- 全域變數裡存的系統指標
    if not S then return nil end
    local keys, cap = ptr(S + keys_off), u32(S + cap_off)
    if not keys or not cap or cap == 0 or cap > 0x40000 then return nil end
    return S, keys, cap
end

-- ptr / u32 都經過 ReadProcessMemory：位址不對只會回傳 nil，不會當掉
這些偏移量綁定遊戲 build 25480438。遊戲更新後位置可能移動：HUD 會退回比較慢的堆積掃描，Plate Fix 則停止動作，需要照第 3 步重新找一次。

extern HealthSystem* g_health_system;

struct KeyValue { uint32_t entity, index; };

struct HealthSystem {
    // ...
    /* +0x1030 */ KeyValue*     keys;
    /* +0x1038 */ uint32_t      capacity;
    /* +0x103C */ uint32_t      empty_key;
    /* +0x1040 */ uint32_t      multiplier;
    // ...
    /* +0x1058 */ HealthRecord* records;  // 每筆 0x1B8 bytes
};

uint32_t find_index(HealthSystem* hs, uint32_t entity) {
    uint32_t mask = hs->capacity - 1;
    uint32_t h    = hs->multiplier * entity;
    for (uint32_t i = 0; i < hs->capacity; ++i) {
        KeyValue& kv = hs->keys[(i + h) & mask];
        if (kv.entity == hs->empty_key) break;   // 沒有
        if (kv.entity == entity) return kv.index;
    }
    return NOT_FOUND;
}

  2. 組合語言裡的 [暫存器 + 位移] 就是結構欄位，[rip + X] 就是全域變數。
  3. 找出遊戲自己用來找資料的那個全域變數，模組就有了固定、可靠的起點。

直接讀 vs ReadProcessMemory

用 FFI 把位址轉成指標直接讀，位址錯了就是存取違規、遊戲當掉（第 6 章）。Recon 的做法是先用 VirtualQuery 問「這段能不能讀」再讀，但「問」和「讀」之間有極短的空檔，遊戲的其他執行緒可能剛好在這個空檔把記憶體釋放掉。

ReadProcessMemory 沒有這個空檔：讀不到就回傳失敗，不會當掉。所以要給玩家用的 HUD 和 Plate Fix 一律用它讀自己的程序；Recon 是開發用工具，才接受直接讀的小風險。HUD 的離線測試也實際抓到過：直接讀堆積時，記憶體在檢查和讀取之間被釋放，測試程式當掉。

「釋放」不等於「消失」：舊副本

C++ 程式歸還一塊記憶體，或陣列長大時搬到新位置，舊的那塊通常只是交還給程式自己的配置器，內容還在、也還讀得到，只是遊戲不再更新它。如果模組是「在記憶體裡搜尋」找資料，就可能找到這種舊副本：指紋完全正確，數值卻凍結不動。

每次讀都要驗證

  • 每次讀紀錄都重新檢查指紋（39 個裝甲值 + 0xFFFF 標記）和數值範圍（每個部位的 HP 不能超過最大值）。任何一項不符，就當作沒找到，不用這筆資料。
  • 遊戲會搬家：每幀都重新從全域變數讀陣列位置，每秒用實體編號重新查一次第幾筆。
  • 找不到時有退路：全域變數讀不到（例如遊戲更新後位置變了），就退回比較慢的堆積搜尋，並在 log 寫下原因。

時間預算

搜尋堆積要讀好幾 GB 的記憶體，一次做完會讓那一幀卡住好幾秒。所以要切成小塊，每幀只做一點。HUD 一開始每幀花 8 ms，在 130 FPS 時讓 FPS 掉了一半，後來降到 4 ms。改成直接走全域變數之後，平常每幀的成本只剩零點幾毫秒。

Hive Lord HUD 此時（10/05）：玩家回報「板子已經炸了，面板還顯示 20 幾 %」。查 log 發現，HUD 的堆積搜尋在某次重新搜尋時採用了一份舊副本，之後 130 秒數值都沒變。這就是 v83 改成從全域變數出發（第 10 章）的直接原因。改完之後一整場戰鬥只需要找一次，再也沒有凍結。
重點
  1. 給玩家用的模組一律用 ReadProcessMemory：位址錯了只失敗、不當掉。
  2. 釋放的記憶體還讀得到，搜尋可能找到凍結的舊副本；從遊戲自己的指標出發才可靠。
  3. 每次讀都驗證、每幀都有時間上限、失敗時有退路並寫 log。
自我檢查：舊副本「指紋完全正確」，那要怎麼防？

指紋只能證明「這是 Hive Lord 的紀錄」，不能證明「這是遊戲正在用的那一份」。所以不能靠搜尋，要從遊戲自己的全域變數和雜湊表找：遊戲當下用哪一份，那條路就指向哪一份。

每個模組都該有的幾條規則

  1. 單例守衛：開頭先檢查一個獨特的全域變數，已經存在就不再執行。
  2. 環境檢查：需要的 API、Loader 不在，就寫 log 並停手，而不是硬跑。
  3. 包裝 update，出錯就解除武裝：每幀工作包在 pcall 裡，第一次出錯就永久關閉自己、清掉畫面，並寫下原因。
  4. 一定呼叫原本的 update。
  5. 呼叫前先確認：world 還在、unit 還活著（引擎錯誤救不回來）。
  6. 時間預算與自我計時：量每幀花了多少，定期寫進 log。
  7. log 要限流：只寫狀態改變，不要每幀一行。

跟別的模組合作：設定選單

Mod Options Menu 也是一個透過 Loader 載入的模組，它在全域放了一個 ModOptionsMenu 表，其他模組可以呼叫 register_option 註冊設定、用 get 讀值。因為模組之間的載入順序不保證，所以 HUD 不在載入時找它，而是在 update 裡才找，找到了才註冊。沒有裝它，HUD 就用設定檔裡的值。

Hive Lord HUD 此時（10/04，v72–v78）把所有設定搬進 Mod Options Menu，拿掉所有快捷鍵。過程中學到：選單的修改要按遊戲的「套用」才生效，按 Esc 會丟掉，所以「預覽」改成按鈕式：套用後顯示 15 秒，再自己把選項切回關。（10/07，v116）功能凍結後做了一次大整理：3,568 行減到約 2,600 行，研究用的診斷移到另一個開發用模組。
重點
  1. 模組骨架：單例守衛 → 環境檢查 → 包裝 update（pcall + 解除武裝）→ 每幀工作。
  2. 每條規則都對應前面的一個原理，大多是當掉之後才補上的。
  3. 模組之間可以合作，但不能假設載入順序。
自我檢查：為什麼「出錯就永久關閉」比「出錯就下一幀再試」好？

同一個錯誤下一幀通常還會再發生。一直重試會每幀都出錯、把 log 灌爆，還可能在錯的狀態下繼續呼叫引擎 API 而讓遊戲當掉。永久關閉只損失這個模組的功能，遊戲安全，log 裡也留下第一次出錯的原因。

這一章要回答每次進遊戲測試都要重開、還可能當掉。能不能在電腦上就先抓到大部分的錯？
新概念
lupa
在 Python 裡執行 Lua 的套件，有 LuaJIT 版本。
假物件（stub）
模仿遊戲 API 的假函式。
變異測試
故意把程式改壞，確認測試會失敗。

原理：模組只透過三個管道跟遊戲互動——引擎 API、FFI 讀記憶體、Loader。只要把這三個管道換成假的，模組就分不出自己是不是在遊戲裡。

  • 同款的 Lua：用 lupa 的 LuaJIT 版本執行真正的模組原始碼。用新版 Lua 的話，// 這類遊戲不支援的語法會通過測試，進遊戲才載入失敗。
  • 假的引擎：自己寫 World、Unit、Gui、Camera，記錄模組呼叫了什麼。可以讓它們故意模仿遊戲的壞習慣，例如「對已經死掉的單位呼叫就當掉」，確認模組不會這樣做。
  • 假的記憶體：在真的記憶體裡放一份假的健康系統、雜湊表、血量紀錄，讓模組照真正的路去找。再放幾個「長得像但不對」的誘餌，確認驗證會擋下它們。
  • 變異測試：把程式故意改壞（例如拿掉指紋檢查），測試必須失敗。抓不到故意放的 bug，代表測試沒在檢查東西。
  • 畫面也能離線看：把模組呼叫的 Gui.rect、Gui.text 記錄下來，用 Python 畫成圖片，進遊戲前就能看版面。Hive Lord HUD 的展示圖和模組圖示就是這樣產生的。
Hive Lord HUD 此時有幾十個測試腳本（test_v83.py、test_v108.py…），多數版本都記錄著「殺掉了幾個變異」。它們抓到過不少進遊戲前就會出事的錯，例如：在定義某個表之前就用到它（模組會在遊戲裡直接解除武裝）、診斷用的緩衝區被誤當成血量紀錄採用（它也通過了指紋檢查）。也踩過一個測試本身的坑：測試讀寫的是真正的設定檔，把玩家的設定改掉了，之後所有測試都改成導到暫存資料夾。
重點
  1. 模組跟遊戲的互動只有三個管道，全部換成假的就能離線執行。
  2. 假物件要模仿遊戲的嚴格與壞習慣，誘餌要能騙過不小心的驗證。
  3. 變異測試確認「測試真的有在檢查」。
自我檢查：測試全部通過，進遊戲卻失敗，最可能是哪裡不一樣？

假物件跟真的遊戲不一樣：太寬鬆（真的引擎會當掉的呼叫，假的不會）、資料形狀不同（測試只造了一種記憶體布局），或用了不同版本的 Lua。修法是把那個差異補進假物件，再加一條對應的變異測試。

patch 檔長什麼樣

打包工具做的事，就是把第 1 章的封存檔格式反過來寫一次：標頭、型別表（只有 lua 一種）、檔案表（名稱雜湊、位置、大小），最後是資料。資料本身是「長度 + 2（代表純文字）+ 原始碼」，對齊到 16 bytes。在下面輸入資源名稱和程式內容，看實際的 bytes（跟我們的打包工具算法相同）：

zip 與 manifest

模組管理器匯入的是一個 zip：manifest.json（名稱、說明、選項）、每個選項一個資料夾（裡面是 patch 檔）、Source/（明文原始碼，讓人能審查）。幾個重點：

  • GUID 永遠不變：管理器靠它認出「這是同一個模組的新版本」。Hive Lord HUD 的 GUID 從 v1 到 v3 都是 4ef072f2-…。
  • Name 只用英文、數字、空白：它會被當成資料夾名稱，一個冒號就讓匯入失敗。
  • 選項 = 分開的 patch 檔：Hive Lord HUD 有兩個選項，「Hive Lord HUD」和「Dead Plate Fix」，各是一個 patch 檔，玩家可以只裝其中一個。

部署：管理器會重排編號

Arsenal 每次部署都會重新分配 patch 編號，而且每個選項各佔一個 slot。開發時為了快，我們會直接把新的 patch 檔複製進 data/，這時候不能寫死編號：要用檔案內容（找自己的 -- HD2-Addon: 那一行）確認哪個 slot 是自己的，並且同時更新 Arsenal 自己保存的那份副本，否則下次 Deploy 會把舊版放回去。遊戲執行中也不能部署：Lua 只在啟動時載入。

Hive Lord HUD 此時（10/04）因為寫死編號吃了虧：Arsenal 重排之後，我們複製到 patch_1 的新版蓋掉了另一個模組（Megapack 的一個選項），遊戲還載入了放在 patch_7 的舊版。之後寫了部署腳本：依內容找出自己的 slot、找不到或找到兩個以上就中止、遊戲在執行就拒絕部署。發佈則用 build_hive_lord.py：Release v1 = 內部 build 70，v2 = build 87（加入 Dead Plate Fix 選項），v3 = build 121。
重點
  1. 打包就是照封存檔格式寫一個只有 lua 資源的 patch 檔，名稱用 murmur64。
  2. manifest 的 GUID 不變、Name 只用安全字元，選項各自一個 patch 檔。
  3. 管理器會重排編號，任何直接部署都要先依內容找到自己的 slot。
自我檢查：如果每次發佈都產生一個新的 GUID，會發生什麼事？

模組管理器會把每一版當成不同的模組。玩家的清單裡會同時出現好幾個 Hive Lord HUD，舊版不會被取代，還可能兩個一起載入。

用戶端看到的不一定是全貌

多人遊戲裡，主機決定很多事（敵人 AI、部位是否被打壞），用戶端只收到結果。HD2 的每台電腦會自己模擬看得到的子彈和傷害，主機只送「狀態改變」「死亡」這類結果。所以用戶端記憶體裡的數字，可能跟主機不一樣，而模組只讀得到自己這台的。

這也決定了用戶端模組做不到的事：例如「讓 Hive Lord 不要跑太遠」，AI 在主機上跑，用戶端的模組改不了。

遊戲更新時 game.dll 會重新編譯：函式和全域變數的位置（RVA）、結構的位移、資料表的大小都可能改變。本文所有的位址都只對 build 25480438 有效。所以模組要設計成「對不上就安全停手」：

  • 每次讀都驗證指紋，不對就不用（第 11 章）。
  • 主要的路失效時有退路（HUD 退回堆積搜尋；Plate Fix 直接停止動作）。
  • log 寫清楚「為什麼停手」，玩家回報時才知道是更新造成的。
  • Loader 本身也綁定遊戲版本，大更新後要等 Loader 先更新。
Hive Lord HUD 此時為了誠實面對多人的限制，加了「<」標記：中途加入、或發現主機修正過我們的數字之後，板子的 % 和主血前面會加「<」，代表「最多剩這麼多」。也研究過能不能讓主機送出真實血量，結論是路不通，而且送網路請求會影響別人的遊戲，所以不做。
重點
  1. 用戶端模組只看得到自己這台電腦的資料，主機決定的事改不了。
  2. 顯示的數字要誠實標出不確定性。
  3. 遊戲更新會讓位址失效，模組要「對不上就安全停手」。

GameGuard 會做什麼

GameGuard（nProtect）是 Helldivers 2 的反作弊，由一個核心驅動程式和跟遊戲一起啟動的監控程序（GameMon）組成。它的內部細節沒有公開，以下是從它的行為和我們實際遇到的狀況整理的：

它做的事我們實際看到的
掃描電腦上的程式，比對已知作弊工具的特徵電腦上有被判定為作弊工具的程式時，遊戲會跳出「Suspicious program detected」並關閉。號稱能繞過反作弊的工具尤其危險，很多本身就是木馬。
保護遊戲程序：擋外部程式開遊戲的 handle 去讀寫記憶體或注入（把自己的程式碼塞進遊戲程序裡執行），偵測除錯器遊戲崩潰後程序殺不掉（Task Manager 結束「成功」但程序還在），只能重開機。
檢查程式碼完整性：定期對程式碼區段算雜湊所以我們從不修改 code bytes、不 hook 函式。
每次啟動自我更新，log 加密且每次啟動輪替log 無法自己解讀，有問題只能交給 Arrowhead 客服。

另外，game.dll 本身用 Themida 加殼，這是另一套保護，不屬於 GameGuard。硬碟上的 game.dll 是加密的，只有載入記憶體後才是解開的程式碼。

  • 加殼（Themida）：把程式碼加密，執行時才在記憶體裡解開。所以硬碟上的 game.dll 讀不出東西，要從執行中的記憶體 dump 出來才能分析。
  • 殭屍程序：遊戲崩潰後，程序仍受反作弊保護，工作管理員結束不掉，只能重開機。開發時遇到好幾次。
  • 程式碼雜湊檢查：定期對程式碼區段算雜湊（第 3 小節），只要有 1 個 byte 被改就對不上。這也是為什麼模組從不修改程式碼。

為什麼 Plate Fix 讀寫記憶體，GameGuard 卻不管

因為 GameGuard 主要防的是「外面的程式動遊戲」，而 Plate Fix 是遊戲自己在動自己的記憶體。從作業系統的角度看，這是兩件完全不同的事。

1. 不跨程序

外掛通常是另一個 exe：OpenProcess 拿遊戲的 handle，再讀寫記憶體。GameGuard 的驅動就在這一步攔截。Plate Fix 是遊戲內建的 LuaJIT 在執行，用的 WriteProcessMemory(GetCurrentProcess(), …) 是「自己」的虛擬 handle（-1），不需要開任何外部 handle，根本不經過被攔的那一步。對系統來說，這跟遊戲自己執行 *p = x 一樣，只是多了「位址錯了回傳失敗、不會當掉」的保護。

2. 寫的是資料，不是程式碼

程式碼不會變，所以能算雜湊比對；HP、遮罩、座標這些資料遊戲自己每秒要寫上百萬次，沒辦法檢查有沒有被改。Plate Fix 只寫遮罩 entry 裡的 1 個 byte，而且寫的值跟 gore 本來就會寫的一模一樣，是遊戲正常運作時本來就會出現的狀態。

3. 它掃的是作弊程式，不是遊戲資源

GameGuard 比對執行中的程式和已知的外掛特徵，不會逐一檢查遊戲載入的 Lua 資源在做什麼。整個 Bingus 模組圈都這樣運作，例如 Megapack 的 Enemy Collision Synchronized 直接用 FFI 呼叫 game.dll 內部函式，第一人稱模組會配置可執行記憶體、替換 Camera API 的函式指標，都比 Plate Fix 侵入得多，也一樣沒被擋。

4. 伺服器端沒有東西可以發現

Plate Fix 不改傷害、碰撞、網路封包，只改你自己畫面上的一個模型遮罩。主機和其他玩家收不到任何差異。

為什麼插進去的資料和 Lua 不會被抓

一句話：GameGuard 這類反作弊找的是外來的程式碼和外來的存取（注入的 DLL、外部程式開的 handle、被改過的程式碼、已知的外掛程式）。模組加進去的是資料，然後由遊戲自己本來就有的程式碼去讀、去執行。從它的角度看，跟遊戲正常運作分不出來。逐層來看：

我們加了什麼誰去讀 / 執行它為什麼不會被當成作弊
patch 檔
data/9ba626afa44a3aa3.patch_N		遊戲自己的資源系統（Stingray 引擎）用 patch 檔蓋過原版資源是引擎本來就有的機制。遊戲執行時不驗證資源檔簽章（否則所有模組都載不進去），只有 Steam「驗證檔案完整性」時才會比對，而那會直接把檔案換回原版。反作弊不檢查遊戲資源檔的內容。
Lua 原始碼（純文字）遊戲自帶的 LuaJIT（bin/lua51.dll，2.1 版）沒有載入任何新的 DLL、沒有建立外部執行緒、沒有改任何一個 byte 的程式碼。對作業系統來說，只是遊戲自己的直譯器在處理一段文字。
JIT 產生的機器碼LuaJIT 把常跑的 Lua 編譯成機器碼，放在它自己配置的可執行記憶體這是遊戲跑任何 Lua 時本來就會做的事（Loader v18 調大的就是這塊快取）。反作弊如果禁止「程序裡出現新的可執行記憶體」，會連遊戲自己的 Lua 一起擋掉。
FFI 呼叫 Windows API
ReadProcessMemory 等		遊戲程序自己呼叫 kernel32呼叫者就是遊戲程序本身，用的是自己的虛擬 handle（-1），沒有任何「外部程式碰遊戲」的動作。
寫入的那 1 個 byte（Plate Fix）遊戲的遮罩更新函式下一幀讀到它寫在資料區，值跟 gore 本來會寫的一樣；程式碼雜湊檢查只看程式碼區段。

對照一下真正的外掛通常怎麼做：另一個 exe 開遊戲的 handle（被驅動攔截）、把 DLL 注入遊戲（多出一個不認識的模組）、修改程式碼讓子彈無限（程式碼雜湊對不上）。這三件事模組都沒有做。

這也說明了為什麼 GameGuard 擋得住外部的 Cheat Engine，卻擋不住 Recon：Recon 讀記憶體用的跟 Plate Fix 是同一條路。所以界線不在技術，而在做什麼：我們的模組只讀資料、只改自己畫面上的東西，不影響傷害、碰撞、網路，也不碰其他玩家。

「沒被擋」不等於「被允許」。這仍然是非官方修改，GameGuard 隨時會自動更新、加入新的檢查。所以設計上堅持：不碰程式碼、不送封包、只寫跟遊戲原本行為一模一樣的值。萬一規則改變，風險和影響範圍也盡量小。

不碰程式碼

不修改任何 code bytes（不會觸發 GameGuard 的程式碼雜湊檢查），不 hook 函式，不送網路封包。只呼叫引擎開放給 Lua 的 API 和 Windows 的記憶體讀寫 API。

出錯就退出

整個每幀邏輯包在 pcall 裡：第一次 Lua 錯誤就永久解除（拆掉 Gui、寫 log），原本的 update() 照常執行，遊戲不受影響。

記憶體存取

只用 Read/WriteProcessMemory，位址錯了只會回傳失敗。每次讀都重新驗證指紋；任何一項不符就跳過這一步並記錄原因。

引擎呼叫守則

  • 每次呼叫前確認 world 還活著（world_is_live）
  • 對任何單位呼叫前先 Unit.alive(u)
  • Hive Lord 死後完全不碰屍體
  • 完全不呼叫 stingray.Network.*（會讓引擎直接終止）
Hive Lord HUD 此時的設計原則就是這一章：HUD 只讀資料；Plate Fix 只寫一個「這塊板子要不要畫」的 bit，而且是遊戲自己本來就會寫的值；兩者都不改程式碼、不送網路封包、不影響其他玩家。
重點
  1. 反作弊找的是「外來的程式碼和外來的存取」，模組是由遊戲自己執行的資料。
  2. 沒被擋不等於被允許，界線在於做什麼：只改自己的畫面，不影響別人。
  3. 模組的能力等於一般程式，只裝可信、附原始碼的模組。
自我檢查：用同樣的方法做一個「自動瞄準」，技術上做得到嗎？該做嗎？

技術上這扇門確實開著（第 1、2、5 章）。但它給自己不公平的優勢、破壞別人的遊戲，也很容易被封號。這份文件介紹的原理，界線一直是「只影響你自己的畫面和電腦」。

開發方法與工具鏈

原則是「離線優先」：能在電腦上算完、測完的事，就不讓作者進遊戲測。遊戲時間只用來回答離線回答不了的問題。

1. 從遊戲資料離線解答

  • FileDiver（Go）：解遊戲封存檔、datalib、typelib；另外寫了 hive-lord-health-dumper、entity-probe、sm-state-dumper 等小工具。
  • 模型匯出成 glb 看骨架與碰撞節點名稱。
  • 雜湊暴力破解（murmur64(name) >> 32）還原區域名稱。

2. 靜態逆向

  • 遊戲跑起來後用 Recon addon 把已解殼的 game.dll / helldivers2.exe dump 出來。
  • 用 Python + capstone 秒級掃描特定偏移量的存取，找出函式；Ghidra 輔助。
  • 所有發現都寫進研究筆記。

3. 離線測試

  • 用 lupa（Python 內嵌 Lua）載入真正的模組原始碼，搭配假的引擎 API（World、Unit、Gui、Camera…）與假的遊戲記憶體結構。
  • 變異測試：故意把程式改壞（例如拿掉健全性檢查），確認測試會失敗。大多數版本都記錄「殺掉 N 個變異」。
  • 模擬「對已銷毀單位呼叫就崩潰」的 stub，驗證死後 70 秒內 0 次引擎呼叫。

4. 看得到的設計審查

  • 把測試中記錄下的 Gui 呼叫渲染成 PNG（PIL），在進遊戲前就能看到版面。
  • 模擬遊戲的顏色放大，預覽實際效果。
  • 展示圖和模組圖示也由同一套渲染器產生。

5. 遊戲中驗證

  • 作者正常遊玩（永遠是用戶端），HUD 的 log 記錄所需資訊：hostdiag、MAIN JUMP、[PlateFix]、每 30 秒的更新率與每幀成本。
  • 每個實驗性 API 在第一次呼叫前先寫一行 log：如果遊戲當掉，最後一行就是元兇。

6. 建置與部署

  • 打包腳本產生 Arsenal 可匯入的 zip（固定 GUID，選項各自一個 patch）。
  • 部署腳本只覆寫含有我們 addon 標記的 slot，遊戲執行中會拒絕部署。
