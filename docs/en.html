How Helldivers 2 mods work

How can a program the developer never wrote run inside the game? How does it know where the game keeps its data? And how do the modding tools each work? This document follows the process of building the Hive Lord HUD from scratch as its main thread, with one principle per chapter. At the end of each chapter you'll see “where the HUD is at this point”.

The code: compiled machine code

Arrowhead's engineers write the game in C++ (that's the source code), then a compiler translates it into machine code the CPU can run directly. During that translation, variable names, function names and comments all disappear, leaving only a string of bytes. Because all we have is the machine code, if you want to know what the game is doing, you have to work backwards from the machine code (Chapter 10).

Machine code lives in two kinds of files: the .exe is the main program, and a .dll is a library the main program loads while it runs. In Helldivers 2 the work is split like this:

FileWhat it is
bin/helldivers2.exeThe engine: Autodesk Stingray (formerly Bitsquid). Handles graphics, physics, file loading and running Lua scripts. Many games share this same engine.
bin/game.dllGame logic: damage, AI, network sync. Written in C++, and protected by encryption (Chapter 10).
bin/lua51.dllLuaJIT: the program that runs Lua scripts (Chapter 2).
data/Resource files: everything else.

When you hit “Play”, Windows starts helldivers2.exe and it becomes a process, which then loads game.dll and lua51.dll into itself. From that moment on, the engine, the game logic and the scripts all run inside the same process.

Resources: finding files by hash

data/ is full of files with names like 9ba626afa44a3aa3. These are archives, each holding many resources. When the engine wants a resource, it doesn't look it up by a text name. It uses two numbers instead: the type hash and the name hash.

A hash is a formula: the same text always produces the same number, but you can't work back from the number to the text. HD2 uses a formula called murmur64, which produces a 64-bit number. For example, the Hive Lord's model resource is called content/fac_bugs/cha_hive_lord/cha_hive_lord, and its hash is 0xD465D9C7F77A07CB; the hash of the type “lua” is 0xA14E8DFA2CD117E2. Because the files only store the numbers, you can't see any names just by opening an archive; you need a name list someone else has compiled to translate them back (Chapter 8).

The key that makes mods possible: patch files override the originals

There's a special kind of archive: files whose names end in .patch_0, .patch_1, and so on, called patch files. When the engine reads a resource, if a patch file contains a resource with the same type and the same name, it uses the version in the patch file and overrides the original. This mechanism was originally meant for game updates.

Because the engine dutifully reads any patch file placed in data/, and never checks whether its contents have been changed, anyone can make a patch file that swaps a resource for their own version. Every HD2 mod (cosmetic swaps and feature mods alike) is built on this.

Hive Lord HUD at this pointJust an idea (Oct 3): “It should be possible to make a Hive Lord health bar that shows the main HP and the HP of each armour plate.” The game itself doesn't show any of this, and it doesn't offer any feature that “lets you add UI”. So to make it happen, our own code has to run inside the game. The first step is knowing this: the code has to go into a patch file to get into the game.
Key points
  1. The game is compiled machine code; we don't have the source code or the names.
  2. Resources are found by the hash of “type + name”; you can't see text names in the files.
  3. A resource with the same name in a patch file overrides the original, and the game doesn't check. This is the root reason mods can exist.
Check yourself: Why does dropping a .dds texture file straight into data/ do nothing at all?

The engine doesn't recognise loose files; it only looks up resources inside archives, by “type hash + name hash”. To make the game use your texture, you have to pack it into a patch archive with exactly the same name hash as the original, so it overrides the original.

Check yourself: If the game checked a digital signature when reading patch files, could mods still exist?

No (at least not this way). A signature check would notice the patch file isn't official and refuse to load it. HD2 doesn't do this check, and that's the only reason mods have a way in.

The game loop

The game keeps repeating: read your input → update the world (enemies move, bullets fly) → draw the screen. Each repetition is called a frame; 60 FPS means 60 frames per second. Everything that “happens over time” happens inside this loop.

The scripting layer inside the engine

The Stingray engine has a built-in Lua runtime, using the LuaJIT version (its syntax is the same as Lua 5.1). Lua is a scripting language: the code exists as plain text, and LuaJIT only reads and runs it at runtime, with no compiling needed beforehand. The engine was originally designed so that most game logic would be written in Lua; but HD2 put almost all of its logic into the C++ game.dll, leaving Lua as just a thin layer of “glue”:

  • When the engine starts, it loads a few Lua scripts (these are also resources in data/, with type lua).
  • Every frame, the engine calls a Lua function named update, plus a few other fixed entry points such as render and shutdown.
  • The engine exposes a set of features Lua can call (for example, listing the objects in the scene or drawing things on screen), called the stingray.* API (Chapter 4).

The CPU mod measured it: the game's own Lua update takes almost no time per frame (close to 0 ms). In other words, the game itself barely uses this Lua environment, but it is always on and gets called every frame.

Why this is the way in for mods

Lua functions are stored in global variables, and global variables can be changed. Because every frame the engine “goes to the global variable update, takes the function there and calls it”, as soon as someone replaces update with their own function, the engine calls the new one on the next frame:

local original = update          -- first, save the game's original update
update = function(...)            -- replace it with our function
    do_my_stuff()                 -- do our own stuff first
    return original(...)          -- then call the original, so the game works as usual
end

This trick of “redirecting a call to yourself, then passing it back to where it was going” is called a hook. These five lines are what let a mod do something every frame.

But there's a catch: this code itself has to be run once first before it can replace update. The game only runs the few Lua scripts it knows about; it won't run an unfamiliar Lua resource. So who runs it that first time? That's the Loader, in the next chapter.

Hive Lord HUD at this pointThe approach was settled: the HUD would be written in Lua and hook onto update to run every frame. The HUD's final entry point (H.install()) is just a beefed-up version of this chapter's five lines, with error protection (Chapter 4) and self-timing added.
Key points
  1. The engine has Lua built in, and calls the global function update every frame.
  2. Global variables can be changed, so replacing update lets you run your own code every frame (a hook).
  3. But someone has to run your code once first, before it gets the chance to replace update.
Check yourself: What happens if you forget to call original(...) in your hook?

The only thing the engine calls each frame is your function, so nothing the game's own Lua layer should do gets done. At best some features stop working; at worst the game breaks. So you must always call the original function and pass its return value back.

Check yourself: HD2's game logic is almost all in C++, so what can a Lua mod still do?

The Lua layer is thin, but it lives inside the game process, gets called every frame, and can use the APIs the engine exposes. Add the FFI from Chapter 5, and Lua can call Windows functions and read the game's memory directly, so it can do far more than “what the game itself uses Lua for”.

The key step: borrow a vanilla script that always runs

Put Chapter 1 and Chapter 2 together and the trick appears: when the game starts it always loads certain vanilla Lua scripts, and a patch file can override a vanilla resource with one of the same name. So if you make a patch file containing a Lua resource with the same name as a vanilla script, the game runs our version at startup.

Bingus Shared Loader picks core/wwise/lua/wwise_flow_callbacks: a callback script that the sound system (Wwise) always loads at startup. But the vanilla script handles sound, so if you just replace it, the game goes silent. So the Loader keeps every feature of the vanilla script, and does one extra thing on top: load mods.

  • The game's resources live in archives in data/, located by “type + name hash (murmur64)”. The mod manager (Arsenal / HD2MM) deploys mods as extra 9ba626afa44a3aa3.patch_N files, and a resource with the same name inside them overrides the vanilla one.
  • The Loader's archive holds just one lua resource, with name hash 0x7251FDD9BB62480A. We ran the same murmur64 and it matches core/wwise/lua/wwise_flow_callbacks exactly: the vanilla script the game's sound system (Wwise) requires at startup.
  • So as soon as the game boots and loads the sound system, what actually runs is the Loader. It keeps all of the vanilla script's Wwise callbacks (wwise_trigger_event, wwise_load_bank…), so sound works as normal; the README also points out that it “keeps Wwise callbacks, does not replace boot”.
  • The Loader itself is compiled LuaJIT bytecode (header \x1bLJ, about 20 KB). The flow below was pieced together from string constants in the bytecode, the README, and real logs.

What the Loader does after it starts

  1. Enlarge the LuaJIT JIT cache: every mod shares the game's single LuaJIT, and the default cache is too small, so with many mods installed it keeps getting flushed. v18 raises it right away to 16 MB / 8,000 compiled code pieces (traces), grows it to 64 MB / 16,000 after a flush, and writes a LuaJIT cache: line to the log.
  2. Create the shared log folder %LOCALAPPDATA%\CowboyBingus\Helldivers2\Logs and open BingusSharedLoader.log.
  3. Create the global table CowboyBingusModLoader: it holds the version, the API level, a list of mod states, open_log(filename) (only accepts file names like ^[%w_-]+%.log$, so a mod cannot write to some other path), and JIT cache stats (jit.flushes and so on).
  4. Find the game's data folder: use GetModuleFileNameA to get the executable's path, check that it ends in /bin/helldivers2.exe (if not, stop), and work out /data/ from it.
  5. Scan every patch file: FindFirstFileA lists 9ba626afa44a3aa3.patch_*; each one is opened, the archive magic number 0xF0000011 and the tables are checked, the start of each lua resource is read, and its first line is matched against this pattern: 
    ^%-%- HD2%-Addon: (mods/[A-Za-z0-9_]+/[A-Za-z0-9_/]+)
    The bytecode also contains a murmur64 implementation (hasher), which looks like it checks that the declared name matches the resource's hash (a guess, not confirmed in source).
  6. Load: for the auto-discovered addons, plus a built-in list of CowboyBingus mods, check each one with Application.can_get('lua', name): if it does not exist, log not installed; if it does, run pcall(require, name) and log loaded on success, or load failed: reason on failure.

Why there is one “shared” Loader

For any one resource, only one patch can win. If every mod overrode wwise_flow_callbacks on its own, only the last one would take effect and all the others would vanish. So the community uses one shared Loader to hold that entry point, and it loads all the mods in turn. Your mod does not need to override any vanilla resource. It just ships a Lua resource with a new name, and puts -- HD2-Addon: … on the first line so the Loader can find it.

The mod manager (Arsenal, HD2MM) writes each mod as one patch file in data/. Every time it deploys, it reassigns the patch numbers, so you cannot assume your mod always sits at a fixed number (you will run into this again in Chapter 14).

Can it work without the Loader?

No. Our mod is just a lua resource called mods/hivelordhud/hive_lord_hud, and nothing in the game itself ever requires that name. Without the Loader, the resource gets deployed into the game folder but never runs: no error, and no effect at all.

  • The only fallback in the code for “no Loader” is writing the log to %TEMP% instead. But that still assumes the mod was loaded, so in practice it never gets used.
  • The settings menu disappears too: Mod Options Menu is itself a mod loaded by the Loader.
  • In theory you could copy the Loader and replace a vanilla script yourself as an entry point. But only one patch can win per resource, so you would clash with the Loader and other mods, and you would have to maintain the vanilla script's features yourself — so we don't. That is the whole point of the Loader: all mods share one entry point instead of fighting over the same vanilla script.

So the install instructions list Bingus Shared Loader as a required dependency; Mod Options Menu (Megapack) is optional, and without it the HUD runs with default settings.

Common pitfalls
  • The game uses LuaJIT (Lua 5.1 syntax). Things that only arrived in Lua 5.3 or later, like // integer division, string.pack and math.type, do not work. Offline tests must use the LuaJIT build of lupa (a package for running Lua from Python); otherwise the tests pass and you only get load failed in the game.
  • All mods share the same Lua VM and the same set of FFI declarations: wrap ffi.cdef in pcall (another mod may have declared it first), and give global variables unique names.
  • In Arsenal, the Loader must sit at the bottom of the list (default priority). If you change the order, do Purge + Deploy.
  • The Loader is tied to the game version. After a big game update, wait for the Loader to be updated.
Hive Lord HUD at this point For its first 69 versions, the HUD was actually packed into the same mod as our research tool Recon (Chapter 9), loaded by the Loader. Only at v70 did it split off and get its own resource name, mods/hivelordhud/hive_lord_hud. The later Dead Plate Fix is a second resource, mods/hivelordhud/plate_fix, and is a separate option you can tick on its own in Arsenal.
Key points
  1. The Loader uses a patch file to override a vanilla script that “the game always loads at startup”, and keeps that script's original features.
  2. The Loader then scans every patch file, finds mods by their first line -- HD2-Addon:, and runs require on each one.
  3. Only by sharing one entry point do mods avoid overriding each other.
Check yourself: What happens if you compile your mod's Lua to bytecode before packing it?

The Loader cannot recognise it: bytecode drops comments, so the first-line -- HD2-Addon: is gone. The mod gets deployed into the game but never runs, and never shows up in the Loader's log.

Check yourself: When a mod “does nothing”, which file should you check first, and why?

BingusSharedLoader.log. It records whether each mod was found, and whether it is loaded or load failed: reason. If your mod is not in the list at all, the problem is in packing or deployment; if it says load failed, the problem is in the code itself.

What the engine gives you

The engine opens part of its features to Lua; this is called the API. Mods use these groups the most:

  • Application: the whole game. For example, Application.worlds() lists every current world (scene: the ship, a mission, and a menu are each one).
  • World / Unit: World.units(world) lists every unit in a scene (a monster, a player, and a camera are all units). Unit.resource_name(u) tells you which model resource it uses (it returns a hash). Unit.node(u, 'head') finds the bone named head, and then you read its position.
  • Camera: Camera.world_to_screen turns a 3D position into screen coordinates.
  • Gui: draws rectangles, text and triangles on screen.

Note: the unit a script gets is only a handle (a ticket number), not the location of its data. You can use it to ask the engine questions, but you cannot go from it straight to the monster's HP data. And the engine does not offer any API like “read this monster's HP”. That fact decides the HUD's path from here on (Chapter 5).

Example: how the HUD finds the Hive Lord

  • Every 2 seconds it scans World.units() for each world in Application.worlds() and compares Unit.resource_name. The release build returns a hashed IdString64, so it matches either the path string hive_lord or the hash d465d9c7f77a07cb (= murmur64 of content/fac_bugs/cha_hive_lord/cha_hive_lord).
  • A newly appeared world is left alone until it has been stable for 10 seconds. main_world() changes about every 3 seconds, so you cannot rely on it.
  • The HUD draws on “the stable world with the fewest units” (the UI world; the game world has thousands of units). Once a world disappears, its Gui disappears with it: just forget it, and never call destroy again.
  • A unit value is a handle, not a pointer, so you cannot go from a unit straight to its component memory. HP has to be found another way (next section).
  • After the Hive Lord dies, the HUD fades out over 2.5 seconds, and 1.5 seconds later it never touches that corpse again; it remembers the address and skips it in later scans. This avoids a situation that crashes the game (see “Pitfalls we hit”).

Drawing: the retained-mode Gui

The engine's Gui uses retained mode: Gui.rect(...) creates a rectangle and gives you an id; after that you use Gui.update_rect(id, ...) to change its position, size and colour; when you no longer need it, you destroy it. It does not clear the screen and redraw everything each frame.

  • Each group fades in and out over 0.35–0.6 seconds, and is only destroyed once the fade-out finishes.
  • A primitive is only sent to the Gui when its colour, size, position or text changes; nothing is sent on the frame it is created (text created and updated in the same frame never shows up in the game).
  • Arguments must be real engine objects: Vector3(x, y, layer), Vector2(w, h), Color(a, r, g, b).
  • Each facet of the low-poly panel is a real Gui.triangle. Its points must be written as Vector3(x, 0, y) (confirmed by disassembling helldivers2.exe: y and z are swapped). If creating a triangle fails, it automatically falls back to building it from 2 px rectangle strips.
  • The font is core/performance_hud/debug, which is already in the base archive; bold is a copy of the same text drawn 1 px to the right.

What happens when you get it wrong: two kinds of errors

  • Lua-level errors (for example, adding to nil): these can be caught with pcall. So all of the mod's per-frame work is wrapped in pcall; on an error it switches itself off for good, and the game carries on.
  • Errors inside the engine: every engine API has self-checks inside (assert). If an argument is wrong or the object no longer exists, it ends the whole game outright. pcall cannot catch this, because the error never gets back to Lua.

Because the second kind of error cannot be recovered from, the mod must make sure, before each call, that nothing will go wrong: is the world still there, is the unit still alive, are the arguments in the right format? Almost every one of these rules was learned after a crash (see below).

Hive Lord HUD at this point It crashed several times in a row, and each crash taught a rule:
  • v0: called Gui.rect every tick to create new rectangles and never destroyed them, piling up about 2,400 per second; the game hard-froze after 1 minute and after 3.5 minutes. Switched to proper retained-mode usage.
  • v27: drew text with the game's native font; it crashed on the first draw and left a game process that could not be closed, so the only fix was a reboot. From then on, only the debug font from the base resources is used.
  • v42–v64: when a player died, or the Hive Lord's corpse was removed after death, the HUD was still calling the API on units that were already gone. Changed to check Unit.alive(u) before every call, and to never touch the Hive Lord again after it dies.
  • v40: Unit.world_position(u, 0) returned the origin for every unit, so distance was always 0 m. Switched to named bones (head, root).
Key points
  1. The engine API lets a mod look at the scene, find objects and draw on screen, but anything it does not offer (like reading HP) cannot be done.
  2. Lua errors can be caught; errors inside the engine end the game outright, so you must “check before you call”.
  3. The Gui is retained mode: create once, modify afterwards, and remember to destroy.
Check yourself: The mod is already wrapped in pcall, so why can the HUD still crash the game?

The crash happens inside the engine (a failed assert, or touching an object that no longer exists). The error never gets back to Lua, so pcall never gets a chance to catch it. The only fix is to stop that kind of call from happening.

Check yourself: The HUD can find the Hive Lord with World.units, so why can't it read its HP?

What it gets is only a handle, not the location of the data, and the engine offers no API for reading HP. HP lives in memory managed by game.dll, and you have to read it yourself using the methods in Chapter 5.

What FFI is

LuaJIT has a feature that standard Lua does not: FFI (Foreign Function Interface). It lets Lua call functions written in C directly, including the Windows API, and it can also allocate, read and write a block of memory directly. The game's lua51.dll does not switch this feature off.

local ffi = require('ffi')
pcall(ffi.cdef, 'int QueryPerformanceCounter(int64_t* counter);')  -- tell FFI what the function looks like
local kernel32 = ffi.load('kernel32')                               -- load the dll that holds the function
local buf = ffi.new('int64_t[1]')                                   -- allocate a block of C memory
kernel32.QueryPerformanceCounter(buf)                               -- call the Windows API
print(tonumber(buf[0]))                                             -- value of the high-resolution timer

With FFI, what a mod can do suddenly becomes “whatever a normal Windows program can do”:

  • CPU Thread Optimizer uses it to call the Windows thread API and decide which core each game thread runs on.
  • The HUD uses it to call ReadProcessMemory and read the game process's own memory.

Why FFI is also dangerous

  • No safety net: get a function declaration wrong, pass a wrong argument, or read an address you shouldn't, and the game crashes on the spot. pcall can't catch it (Chapter 6 explains why).
  • All mods share one Lua environment: declaring the same thing twice with ffi.cdef throws an error, so every declaration is wrapped in pcall. Keep the object you get from ffi.load alive, or the dll may be unloaded and its functions stop working.
  • Same power as a normal program: a malicious Lua mod can also read your files and go online. That is why Chapter 16 says “only install mods you trust”.
Hive Lord HUD at this pointSettled that “reading HP” can only go through FFI: use ReadProcessMemory to read game memory. But that immediately turns into two questions: where in memory is the HP? And what does the data there look like? To answer them, you first need to understand memory (Chapter 6) and how the game organises its data (Chapter 7).
Key points
  1. FFI lets Lua call the Windows API and work with memory directly. It is the key to mods doing “things the engine doesn't expose”.
  2. It has no safety net: a mistake crashes the game outright.
  3. So a mod has the same power as a normal program. That is both its strength and its risk.
Check yourself: if the game's LuaJIT had FFI switched off, could the HUD still be built?

Not the HP bars or the panel: the engine has no API for reading HP, so the only way is reading memory through FFI. Parts that use only the engine API, like markers and the emerge warning, would still work.

What a number looks like in memory

Memory is one long row of cells. Each cell is 1 byte (0–255), and each cell has a number called its address. Addresses and contents are usually written in hexadecimal (starting with 0x, each digit 0–9, A–F). An integer like HP is usually stored in 4 bytes, called an int32, and the “low byte comes first”, so 150,000 = 0x000249F0 sits in memory as F0 49 02 00:

Every process has its own set of addresses

The addresses a program sees are not the real locations on your RAM sticks. Windows gives every process its own virtual memory, managed in 4 KB pages, which are mapped to physical RAM (or parked on the SSD for a while).

This has three results that matter a lot for mods:

  1. Outside programs can't touch the game's memory: the same address means different RAM in two processes. To read the game, an outside program must first ask Windows for a handle to the game (OpenProcess), then ask Windows to read on its behalf. Anti-cheat blocks exactly this step (Chapter 16). But a mod runs inside the game process and uses the game's own addresses, so it never goes through this step.
  2. Reading the wrong address crashes the game: if an address isn't mapped to any page, or the page doesn't allow reading, the CPU raises an access violation and the program ends immediately. This is why Chapter 5 says FFI has “no safety net”.
  3. Code can't be changed directly: pages that hold code are marked “readable, executable, not writable”. To change them, you first have to call VirtualProtect to change the permissions.
Going further: RAM itself and caches

RAM is the CPU's workbench. It is about 1,000 times faster than an SSD, but much slower than the CPU's built-in caches:

Three kinds of region inside a process

  • Code section: the dll's machine code. It doesn't change while running.
  • Data section: variables at fixed locations inside the dll (global variables). They stay in the same place for the whole session.
  • Heap: data the game allocates while running, such as each enemy's HP. Its location differs every match, and the game may even move it.

Two more things make “finding the HP” harder:

  • ASLR: every launch, Windows puts the dll at a different address (to stop attacks). So you can't remember an absolute address like “HP is at 0x7FFF…”. You can only remember “byte number N counted from the start of the dll”, called the RVA. Real address = this launch's base address + RVA.
  • Pointers: data on the heap has no fixed location, but a global variable in the data section holds its address. A “value that holds an address” is called a pointer. Start from a fixed global variable, follow the pointers step by step, and you reach data whose location changes every match.

Key points
  1. In memory, a number is just a few bytes. An int32 is 4 bytes, low byte first.
  2. Every process has its own virtual memory. An outside program has to go through Windows to read it; a mod inside the process doesn't.
  3. Reading the wrong address crashes the game. The dll's location changes every time, so remember RVAs and follow pointers from global variables.
Check yourself: today game.dll is loaded at 0x7FFFB5F70000, and a global variable's RVA is 0x3326688. What is its real address? What about tomorrow?

Today it is 0x7FFFB5F70000 + 0x3326688 = 0x7FFFB9296688. Tomorrow the base address will be different, but the RVA is still 0x3326688 — just add it to tomorrow's base address. That is why you only remember the RVA.

Check yourself: why can't you just hard-code “HP is at 0x29A60000A64” in your code?

HP lives on the heap, and its location changes every match, and even whenever the game moves it. Next time, a hard-coded address points to something else or doesn't exist at all. Reading it gives you wrong data, or triggers an access violation and crashes the game.

Structs and offsets

C++ uses a struct to keep related data together. After compiling, the names are gone; all that's left is “this field starts at byte N from the beginning”, called the offset. How the game manages enemies: ECS

HD2 uses an architecture called ECS: everything in the level is just an entity ID (e.g. one Hive Lord is 0x22A). Data is attached to that ID in bundles called components (HP component, model component…). Each kind of component is managed in one place by a system. The health system keeps every enemy's HP record in one big array.

To get from an “entity ID” to “record number N in the array”, the health system uses a hash table: a fixed-size table where each slot holds {entity ID, record number}. The ID gives a starting slot; if that slot matches, read it, and if not, check the next slot.

Design values and runtime values

“Hive Lord max HP 150,000, each plate 15,000, armour 5” are design values. They are written in the game data tables under data/, and you can read them without the game running (Chapter 8). “This Hive Lord has 118,350 left right now” is a runtime value, and it exists only in that record in memory.

This split is very useful: design values can become a fingerprint. For example, the Hive Lord's 39 armour values (default zone 5, then 6, 10, 5, 5…) never change during a fight, and the combination is very unusual. So if you see a record in memory whose armour fields are exactly these 39 numbers, you can be almost certain it's the Hive Lord's record.

FileDiver is an open-source unpacking tool written by the community. It builds on Chapter 1 and Chapter 7: archives are binary files with a fixed format, names are hashes, and design values are arrays of structs.

How FileDiver works

How the game stores its resources

  • The data/ folder holds a pile of archives named with 16 hex digits. Each archive is split into three files: the main file, .stream (streamed data, e.g. audio) and .gpu_resources (textures, model vertices).
  • Main file format: header (magic number 0xF0000011, type count, file count) → type table → file table (each file's name hash, type hash, and its offset and size in each of the three files) → data. The patch files we build for our own mods use exactly the same format.
  • File names are stored only as a murmur64 hash, not as strings. FileDiver ships a list of about 250,000 known names (hashes/) to turn hashes back into readable paths; anything not in the list can only be shown as a hash. We recovered the Hive Lord's zone names ourselves by brute-forcing the 32-bit hashes (the upper 32 bits of murmur64).
  • When FileDiver opens data/, it reads the tables of every archive and builds a “(name, type) → location” index. Later patches override earlier files with the same name, just like the game does.

What it can export

Models (glTF / glb, two common 3D file formats, with skeleton and animations), textures (png), Wwise audio (ogg / wav), text tables (JSON), animation state machines, prefabs (pre-assembled groups of objects) and more. The ones we used:

  • Hive Lord model: filediver.exe -g <game folder> -i content/fac_bugs/cha_hive_lord/cha_hive_lord.unit --model-format glb. From the names and positions of the bones and collision nodes, we confirmed that spine0 is at the tail end, which bone each plate belongs to, and that the plate above the tail doesn't belong to any zone.
  • Animation state machine (sm-state-dumper): the state names of the locomotion and action layers used by the emerge warning.

Game data tables (datalib)

  • Gameplay values (each enemy's components: health, armour, weapons, explosions…) live in datalib binary blobs (generated_entities.dl_bin and others). A separate type library, dl_library.dl_typelib, describes each struct's field names, types, offsets and sizes. FileDiver's source code includes these blobs and matching Go structs.
  • Pitfall: FileDiver's hand-written Go structs go stale as the game updates. HealthComponent is actually 22,096 bytes with 51 fields; reading it with the old struct gives garbage. So we switched to reading the current field offsets straight from the type library. Another pitfall: the header in front of each blob (the DLInstance header) is 28 bytes, not 24. Get those 4 bytes wrong and everything after is misaligned.

How Recon works

GameGuard blocks external debuggers and memory readers, so you can't look at the game directly with tools like Cheat Engine or x64dbg. Recon's approach is to make the “recon” itself a mod: it runs inside the game, reads its own process's memory with LuaJIT FFI, and writes the results to a log.

The usage loop

  1. Write the commands for this round into %TEMP%\HD2Recon_cmd.lua (plain Lua, e.g. R.scan('48 8B ?? 20')).
  2. Start the game. Once the Loader loads Recon, it first writes the base address, size and sections of game.dll and helldivers2.exe to the log (R.about).
  3. It then reads the command file, compiles it with loadstring, gives it an environment that can call R.* via setfenv, and runs it inside pcall. An error only writes one run error line and doesn't affect the game.
  4. Close the game, read the log, and decide what to check next. Every time you restart the game, the command file runs again.

Reverse engineering means working out what a program does from its behaviour and machine code, without the source code. This guide uses two approaches:

Static analysis

Don't run the program; read the dumped machine code directly. Turn it into assembly language with a disassembler, then look for: who uses a given offset, who reads a given global variable, who calls a given function (this is called a cross-reference, xref).

Dynamic analysis

Observe the program while it runs: read some memory, watch how values change, count how often a function is called. Because anti-cheat blocks external debuggers, we made the observation tool a mod (Recon).

  • Signature (AOB, array of bytes): a byte pattern that can contain wildcards, e.g. 48 8B ?? 20, used to find specific code in memory.
  • Fingerprint: a set of values that never change and are unique enough to confirm “what I found really is what I want”. For example, the armour values of the Hive Lord's 39 zones, which never change during a fight.

Why dump: packing

game.dll is packed with Themida: the file on disk is encrypted and only decrypted in memory when loaded. So disassembling the game.dll on disk just gives you garbage. You have to use Recon's dump_module to save the whole game.dll as already decrypted in memory (about 71 MiB), then analyse that.

Assembly language basics

A disassembler (capstone, Ghidra) turns machine code into assembly language: one very small action per line. For example, this one line of C++:

C++
hp = std::min(hp, -1);   // HP at most -1
Assembly (really appears in game.dll)
mov   eax, [r9+rdx*4+0xf8]  ; read hp from memory
mov   ecx, 0xffffffff       ; ecx = -1
cmp   eax, ecx              ; compare
cmovl ecx, eax              ; keep the smaller one in ecx
mov   [r9+rdx*4+0xf8], ecx  ; write back to memory
  • Registers: rax, rcx, r9… are little slots built into the CPU; data has to be moved into them before any calculation.
  • Square brackets [ … ] = read or write memory at this address. [r9+rdx*4+0xf8] = “record start + zone number × 4 + 0xF8”, which is exactly the offset from Chapter 7.
  • Global variables: mov rdi, [rip + 0x2aa2ec6] = read the value stored at “address of the next instruction + 0x2aa2ec6”. Work out that offset and you get the global variable's RVA.
  • Function arguments: the first 4 go in rcx, rdx, r8, r9; call calls a function; cmp + je/jne compare and jump (that's an if).

How the fixed starting point was found

Four steps

  1. First, learn from the game data which values to look for. FileDiver extracted the Hive Lord's HealthComponent: main HP 150,000, 15,000 per plate, and 39 fixed armour values (5, 6, 10, 5…). This set of numbers is the fingerprint that identifies it in memory.
  2. Search in-game to find the record. Units are handles, so you can't follow pointers to the component. Early versions (v7–v10) therefore scanned the whole heap in time slices looking for this set of numbers. Once found, we dumped the bytes around it and compared which values changed during a fight to work out the record layout: main HP +0x14, armour +0x5C, 38 zone HPs +0xF8, end marker 0xFFFF, 0x1B8 bytes per record.
  3. Work backwards from the code to the global variable that manages these records.
    • Use the Recon addon to dump the whole game.dll as already unpacked in memory (the file on disk is encrypted by Themida).
    • Scan all the code with Python + capstone for instructions that use these offsets (the 0x1B8 stride, +0xF8, +0x14), finding the damage function 0x9235F0 and other health-related functions.
    • All of these functions load the system pointer from the same place, [rip + X], which works out to game.dll + 0x3326688. Then reading how the functions look up the table gives the offsets of the key table, the capacity and the record array.
    • The visibility-mask system +0x3326708 was found the same way: from the gore function 0x903C70 we traced to the mask-setting function 0x721D20, which also loads its system pointer from a global variable. The entry layout (applied / override / touched / base) was worked out by reading the code of the setter and the update function 0x721680.
  4. Use it and verify. The program stores relative offsets (RVAs) and computes the real address at run time with GetModuleHandleA('game.dll') + RVA. Every read re-checks the fingerprint and skips on a mismatch. In-game logs confirmed both are correct: v83 found the record on the first try, and after Plate Fix v3 wrote to it the plate was hidden within 0.1 seconds.

The matching code (hive_lord_plate_fix.lua, excerpt):

local HEALTH_RVA, VIS_RVA = 0x3326688, 0x3326708

local function table_header(base_rva, keys_off, cap_off)
    local base = M.game_base()                -- GetModuleHandleA('game.dll')
    if not base then return nil end
    local S = ptr(base + base_rva)            -- system pointer stored in the global variable
    if not S then return nil end
    local keys, cap = ptr(S + keys_off), u32(S + cap_off)
    if not keys or not cap or cap == 0 or cap > 0x40000 then return nil end
    return S, keys, cap
end

-- ptr / u32 both go through ReadProcessMemory: a bad address just returns nil, no crash
These offsets are tied to game build 25480438. After a game update the locations may move: the HUD falls back to the slower heap scan, and Plate Fix stops acting until you redo step 3 to find them again.

// game.dll+0x3326688
extern HealthSystem* g_health_system;

struct KeyValue { uint32_t entity, index; };

struct HealthSystem {
    // ...
    /* +0x1030 */ KeyValue*     keys;
    /* +0x1038 */ uint32_t      capacity;
    /* +0x103C */ uint32_t      empty_key;
    /* +0x1040 */ uint32_t      multiplier;
    // ...
    /* +0x1058 */ HealthRecord* records;  // 0x1B8 bytes each
};

uint32_t find_index(HealthSystem* hs, uint32_t entity) {
    uint32_t mask = hs->capacity - 1;
    uint32_t h    = hs->multiplier * entity;
    for (uint32_t i = 0; i < hs->capacity; ++i) {
        KeyValue& kv = hs->keys[(i + h) & mask];
        if (kv.entity == hs->empty_key) break;   // not present
        if (kv.entity == entity) return kv.index;
    }
    return NOT_FOUND;
}

// the damage function receives records[index]
apply_damage(g_health_system, entity, /* ... */);

Our Lua uses the same table (HS_KEYS = 0x1030, HS_CAP = 0x1038, HS_RECS = 0x1058), but instead of computing the hash, it reads through the whole key table looking for the entity. It's a bit slower, but it doesn't need to know the details of the hash function, so it won't break if the game changes how it hashes.

Hive Lord HUD at this point (Oct 5, v83): static analysis found that every health function loads the health system from the same global variable, game.dll + 0x3326688 (587 places in game.dll read it). From then on the HUD stopped searching the heap and instead follows the fixed path “base + RVA → health system → hash table → index → +0x14”. This change also fixed the problem from Chapter 11.
Key points
  1. A packed program has to be dumped from memory in its unpacked form before you can analyse it.
  2. In assembly, [register + offset] is a struct field, and [rip + X] is a global variable.
  3. Find the global variable the game itself uses to find its data, and your mod has a fixed, reliable starting point.
Check yourself: Why look for the global variable “the game itself uses” instead of continuing to search the heap for the fingerprint?

The game's own path always points to the copy of the data the game is actually using. A heap search can find a stale copy that was thrown away but is still sitting in memory (Chapter 11), and searching is also slow and time-consuming.

Direct reads vs ReadProcessMemory

If you use FFI to turn an address into a pointer and read it directly, a bad address means an access violation and the game crashes (Chapter 6). Recon first asks VirtualQuery “is this range readable?” and then reads. But there is a tiny gap between the “ask” and the “read”, and another game thread might free that memory right in that gap.

ReadProcessMemory has no such gap: if it can't read, it returns a failure instead of crashing. So the HUD and Plate Fix, which players use, always use it to read their own process; Recon is a development tool, so it accepts the small risk of direct reads. The HUD's offline tests actually caught this once: while reading the heap directly, memory was freed between the check and the read, and the test program crashed.

“Freed” does not mean “gone”: stale copies

When a C++ program gives back a block of memory, or an array grows and moves to a new place, the old block is usually just handed back to the program's own allocator. The contents are still there, and still readable — the game just stops updating them. If a mod finds data by “searching memory”, it may find one of these stale copies: the fingerprint is completely correct, but the values are frozen.

Validate every read

  • On every read of a record, re-check the fingerprint (39 armour values + the 0xFFFF marker) and the value ranges (each zone's HP can't exceed its maximum). If anything doesn't match, treat it as not found and don't use that data.
  • The game moves things around: every frame, re-read the array location from the global variable, and once a second, look up the record index again by entity ID.
  • Have a fallback when nothing is found: if the global variable can't be read (for example, its location changed after a game update), fall back to the slower heap search and write the reason to the log.

Time budget

Searching the heap means reading several GB of memory; doing it all at once would freeze that frame for several seconds. So you split it into small pieces and do a little each frame. The HUD first spent 8 ms per frame, which cut FPS in half at 130 FPS; later it was lowered to 4 ms. After switching to going straight through the global variable, the normal per-frame cost dropped to a fraction of a millisecond.

Hive Lord HUD at this point (Oct 5): a player reported “the plate is already blown off, but the panel still shows 20-something %.” The log showed that during one re-search, the HUD's heap search had picked up a stale copy, and the value didn't change for the next 130 seconds. This was the direct reason v83 switched to starting from the global variable (Chapter 10). After the change, it only needs to find the record once per fight, and it has never frozen since.
Key points
  1. Mods for players should always use ReadProcessMemory: a bad address just fails, it doesn't crash.
  2. Freed memory is still readable, so a search may find a frozen stale copy; starting from the game's own pointers is the reliable way.
  3. Validate every read, cap the time spent each frame, and have a fallback that writes to the log when things fail.
Check yourself: a stale copy has a “completely correct fingerprint”, so how do you guard against it?

A fingerprint can only prove “this is a Hive Lord record”, not “this is the copy the game is using right now”. So you can't rely on searching; you have to go through the game's own global variable and hash table: whichever copy the game is currently using, that path points to it.

Rules every mod should follow

  1. Singleton guard: at the start, check a unique global variable; if it already exists, don't run again.
  2. Environment check: if a required API or the Loader is missing, write to the log and stop, instead of forcing it to run.
  3. Wrap update, and disarm on error: wrap the per-frame work in pcall; on the first error, permanently shut yourself off, clear the screen, and write down the reason.
  4. Always call the original update.
  5. Check before you call: the world still exists, the unit is still alive (engine errors can't be recovered from).
  6. Time budget and self-timing: measure how much time each frame takes and write it to the log regularly.
  7. Rate-limit the log: only write state changes, not one line per frame.

Working with other mods: the settings menu

Mod Options Menu is also a mod loaded through the Loader. It puts a global ModOptionsMenu table in place; other mods can call register_option to register settings and use get to read values. Because the load order between mods is not guaranteed — so the HUD doesn't look for it at load time; it looks for it inside update, and only registers once it finds it. If it isn't installed, the HUD uses the values from its config file.

Hive Lord HUD at this point (Oct 4, v72–v78) moved all its settings into Mod Options Menu and removed all hotkeys. Along the way we learned that menu changes only take effect when you press the game's “Apply”, and pressing Esc throws them away — so “preview” became a button-style option: after you apply it, it shows for 15 seconds, then switches the option back off by itself. (Oct 7, v116) After the feature freeze came a big cleanup: from 3,568 lines down to about 2,600, with the research diagnostics moved into a separate development mod.
Key points
  1. Mod skeleton: singleton guard → environment check → wrap update (pcall + disarm) → per-frame work.
  2. Each rule matches one of the earlier principles, and most were added after a crash.
  3. Mods can work together, but you can't assume a load order.
Check yourself: why is “shut down permanently on error” better than “try again next frame on error”?

The same error usually happens again on the next frame. Retrying over and over means an error every frame, a flooded log, and possibly continuing to call the engine API in a bad state until the game crashes. Shutting down permanently only loses this mod's features; the game stays safe, and the log keeps the reason for the first error.

The principle: a mod only interacts with the game through three channels — the engine API, FFI memory reads, and the Loader. If you replace all three with fakes, the mod can't tell whether it's inside the game or not.

  • The same Lua: use lupa's LuaJIT build to run the real mod source. With a newer Lua, syntax the game doesn't support, such as //, passes the tests and only fails to load once you're in the game.
  • A fake engine: write your own World, Unit, Gui, Camera that record what the mod called. You can make them deliberately copy the game's bad habits, such as “crash if called on a dead unit”, to confirm the mod never does that.
  • Fake memory: put a fake health system, hash table and HP records into real memory, and let the mod find them along the real path. Then add a few decoys that “look right but aren't”, to confirm the validation rejects them.
  • Mutation testing: deliberately break the code (for example, remove the fingerprint check); the tests must fail. If they can't catch a bug you planted on purpose, the tests aren't really checking anything.
  • You can see the screen offline too: record the Gui.rect and Gui.text calls the mod makes, draw them as an image with Python, and you can check the layout before going in-game. The Hive Lord HUD's showcase images and mod icon were made this way.
Hive Lord HUD at this point has dozens of test scripts (test_v83.py, test_v108.py…), and most versions record “how many mutants were killed”. They caught plenty of bugs that would have broken things in-game, for example: using a table before it was defined (the mod would just disarm in the game), and a diagnostics buffer mistakenly accepted as an HP record (it passed the fingerprint check too). We also hit a pitfall in the tests themselves: a test read and wrote the real config file and changed the player's settings, so after that every test was redirected to a temp folder.
Key points
  1. A mod interacts with the game through only three channels; replace them all with fakes and it runs offline.
  2. Stubs should copy the game's strictness and bad habits, and decoys should be good enough to fool careless validation.
  3. Mutation testing confirms that “the tests really are checking something”.
Check yourself: all tests pass, but it fails in the game. What is most likely different?

The stubs differ from the real game: they're too lenient (a call that crashes the real engine doesn't crash the fake one), the data has a different shape (the tests only built one memory layout), or a different Lua version was used. The fix is to add that difference to the stubs, then add a matching mutation test.

What a patch file looks like

The packing tool simply writes the archive format from Chapter 1 in reverse: a header, a type table (only one type: lua), a file table (name hash, position, size), and finally the data. The zip and the manifest

What the mod manager imports is a zip: manifest.json (name, description, options), one folder per option (holding a patch file), and Source/ (plain source code, so people can review it). A few key points:

  • The GUID never changes: the manager uses it to recognise “this is a new version of the same mod”. Hive Lord HUD's GUID has been 4ef072f2-… from v1 to v3.
  • Name uses only English letters, digits and spaces: it becomes a folder name, and a single colon makes the import fail.
  • Options = separate patch files: Hive Lord HUD has two options, “Hive Lord HUD” and “Dead Plate Fix”. Each is its own patch file, so players can install just one of them.

Arsenal reassigns patch numbers on every deploy, and each option takes its own slot. During development we copy the new patch file straight into data/ to save time — so you must not hard-code the number. Use the file contents (look for your own -- HD2-Addon: line) to confirm which slot is yours, and also update the copy Arsenal keeps for itself, or the next Deploy will put the old version back. You also can't deploy while the game is running: Lua is only loaded at startup.

Hive Lord HUD at this point (Oct 4) got burned by a hard-coded number: after Arsenal renumbered, the new version we copied to patch_1 overwrote another mod (one of Megapack's options), and the game still loaded the old version sitting in patch_7. After that we wrote a deploy script: it finds our slot by content, aborts if it finds none or more than one, and refuses to deploy while the game is running.   1. Packing means writing a patch file in the archive format that holds only lua resources, with names hashed by murmur64.
  2. The manifest's GUID never changes, Name uses only safe characters, and each option is its own patch file.
  3. The manager renumbers slots, so any direct deploy must first find your own slot by content.
Check yourself: What happens if every release gets a new GUID?

The mod manager treats each version as a different mod. The player's list shows several Hive Lord HUDs at once, old versions are never replaced, and two of them may even load together.

A client doesn't always see the whole picture

In a multiplayer game, the host decides many things (enemy AI, whether a zone gets broken), and clients only receive the results. In HD2, each machine simulates the bullets and damage it can see, and the host only sends results like “state changed” or “died”. So the numbers in a client's memory can differ from the host's, and a mod can only read its own machine.

The author always joins other people's games as a client, so the HUD has to be honest about one thing: zone HP on a client isn't necessarily true. From 30+ game logs and analysis of the network code in game.dll:

This also decides what a client mod can't do: for example “keep the Hive Lord from running too far”. The AI runs on the host, and a client's mod can't change it.

Game updates change every address

When the game updates, game.dll is recompiled: the locations of functions and global variables (RVAs), struct offsets, and table sizes can all change. Every address in this document is valid only for build 25480438. So a mod should be designed to “stop safely when things don't match”:

  • Verify the fingerprint on every read; if it's wrong, don't use it (Chapter 11).
  • Have a fallback when the main path fails (the HUD falls back to a heap search; Plate Fix simply stops acting).
  • Write clearly in the log “why it stopped”, so when players report it you know the update caused it.
  • The Loader itself is also tied to the game version; after a big update, wait for the Loader to update first.
Hive Lord HUD at this point added the “<” marker to be honest about multiplayer limits: after joining mid-fight, or after finding that the host has corrected our numbers, plate % and main HP get a “<” prefix, meaning “at most this much left”. We also looked into whether the host could send the real HP. Conclusion: the path doesn't work, and sending network requests would affect other people's games, so we don't do it.
Key points
  1. A client mod only sees data on its own computer and can't change what the host decides.
  2. Displayed numbers should honestly mark their uncertainty.
  3. Game updates break addresses; a mod should “stop safely when things don't match”.
Check yourself: Why does the HUD get slower but keep working after a game update, while Plate Fix stops acting entirely?

The HUD only reads data, so when a global variable breaks it can fall back to a heap search that is slower but doesn't depend on addresses. Plate Fix writes the mask, and writing to the wrong place has serious consequences — so whenever the location doesn't match, it writes nothing at all. Better not to fix than to take the risk.

What GameGuard does

  • Packing (Themida): encrypts the code and only decrypts it in memory at run time. So the game.dll on disk is unreadable; you have to dump it from the running process's memory to analyse it.
  • Zombie process: after the game crashes, the process is still protected by the anti-cheat, Task Manager can't end it, and only a reboot helps. We ran into this several times during development.
  • Code-hash check: regularly hashes the code sections (subsection 3); if even 1 byte is changed, the hash won't match. This is also why the mods never modify code.

Why Plate Fix reads and writes memory, yet GameGuard doesn't care

Because GameGuard mainly guards against “outside programs touching the game”, while Plate Fix is the game touching its own memory. From the operating system's point of view, these are two completely different things.

1. No crossing processes

A cheat is usually a separate exe: it calls OpenProcess to get the game's handle, then reads and writes memory. GameGuard's driver intercepts exactly that step. Plate Fix runs inside the game's built-in LuaJIT, and the WriteProcessMemory(GetCurrentProcess(), …) it uses takes the process's “own” pseudo-handle (-1). It never opens any outside handle, so it never goes through the step that gets blocked. To the system, this is the same as the game running *p = x itself, just with the extra protection that a wrong address returns a failure instead of crashing.

2. It writes data, not code

Code doesn't change, so it can be hashed and compared. Data like HP, masks and coordinates is written by the game itself millions of times a second, so there's no way to check whether it was altered. Plate Fix writes only 1 byte in a mask entry, and the value is exactly what gore would write anyway — a state that already appears when the game runs normally.

3. It scans for cheat programs, not game resources

GameGuard matches running programs against known cheat signatures; it doesn't go through the Lua resources the game loads one by one to see what they do. The whole Bingus mod scene works this way. For example, Megapack's Enemy Collision Synchronized calls internal game.dll functions directly through FFI, and first-person mods allocate executable memory and swap function pointers in the Camera API. Both are far more invasive than Plate Fix, and neither gets blocked.

4. Nothing for the server side to notice

Plate Fix doesn't change damage, collision or network packets; it only changes one model mask on your own screen. The host and other players receive no difference at all.

Why the data and Lua we add don't get caught

In one sentence: anti-cheat like GameGuard looks for foreign code and foreign access (injected DLLs, handles opened by outside programs, modified code, known cheat programs). What a mod adds is data, which is then read and run by code the game already has. From the anti-cheat's point of view, it can't be told apart from the game running normally. Layer by layer:

What we addWho reads / runs itWhy it isn't treated as cheating
patch file

The game doesn't verify resource file signatures at run time (otherwise no mod could load at all); only Steam's “Verify integrity of game files” compares them, and that simply swaps the files back to the originals. Compare that with how real cheats usually work: a separate exe opens the game's handle (intercepted by the driver), injects a DLL into the game (an unknown module shows up), or modifies code for infinite bullets (the code hash no longer matches). Mods do none of these three things.

This also explains why GameGuard can block an outside Cheat Engine but not Recon: Recon reads memory the same way Plate Fix does. So the line isn't technical — it's about what you do: our mods only read data and only change things on your own screen. They don't affect damage, collision or networking, and they don't touch other players.

“Not blocked” doesn't mean “allowed”. This is still an unofficial modification, and GameGuard can auto-update and add new checks at any time. So the design sticks to: don't touch code, don't send packets, and only write values identical to the game's own behaviour. If the rules ever change, the risk and the impact stay as small as possible.

Don't touch code

Never modify any code bytes (so GameGuard's code-hash check is never triggered), never hook functions, never send network packets. Only call the APIs the engine exposes to Lua and the Windows memory read/write APIs.

Exit on error

All the per-frame logic is wrapped in pcall: on the first Lua error the mod disarms permanently (tears down the Gui, writes the log), the original update() keeps running as usual, and the game is unaffected.

Memory access

Only Read/WriteProcessMemory is used, so a wrong address just returns a failure. Every read re-verifies the fingerprint; if anything doesn't match, that step is skipped and the reason is logged.

Engine call rules

  • Before every call, confirm the world is still alive (world_is_live)
  • Call Unit.alive(u) before calling anything on a unit
  • Never touch the Hive Lord's corpse after it dies
  • Never call stingray.Network.* (it makes the engine terminate immediately)
Hive Lord HUD at this point follows exactly the design principles of this chapter: the HUD only reads data; Plate Fix only writes one bit saying “should this plate be drawn”, and it's a value the game itself would write anyway; neither one changes code, sends network packets, or affects other players.
Key points
  1. Anti-cheat looks for “foreign code and foreign access”; a mod is data that the game runs itself.
  2. Not blocked doesn't mean allowed. The line is what you do: only change your own screen, never affect others.
  3. A mod can do anything a normal program can, so only install trusted mods that ship with source code.
Check yourself: Could you use the same method to build an “aimbot”? Technically possible? Should you?

Technically, the door really is open (Chapters 1, 2 and 5). But it gives you an unfair advantage, ruins other people's games, and can easily get you banned. The line for the principles in this document has always been “only affect your own screen and your own computer”.

Development method and toolchain

The principle is “offline first”: anything that can be computed and tested on the PC never needs the author to go into the game. Game time is only used to answer questions that can't be answered offline.

1. Answer from game data, offline

  • FileDiver (Go): decodes the game's archives, datalib and typelib; small extra tools were written too, such as hive-lord-health-dumper, entity-probe and sm-state-dumper.
  • Models exported to glb to see the skeleton and collision node names.
  • Hash brute-forcing (murmur64(name) >> 32) to recover zone names.

2. Static reversing

  • With the game running, the Recon addon dumps the already-unpacked game.dll / helldivers2.exe.
  • Python + capstone scans for accesses to a specific offset in seconds to find functions; Ghidra helps.
  • Every finding goes into notes such as tools/research/hive_lord_armor_break.md.

3. Offline tests

  • lupa (Lua embedded in Python) loads the real mod source code, together with a fake engine API (World, Unit, Gui, Camera…) and fake game memory structures.
  • Mutation testing: deliberately break the code (for example, remove a sanity check) and confirm the tests fail. Most builds record “killed N mutants”.
  • A stub that simulates “calling on a destroyed unit crashes” verifies 0 engine calls within 70 seconds after death.

4. Design review you can see

  • The Gui calls recorded during tests are rendered to PNG (PIL), so you can see the layout before going into the game.
  • The game's colour boost is simulated to preview the real result.
  • The showcase images and the mod icon come from the same renderer.

5. In-game verification

  • The author plays normally (always as a client), and the HUD's log records what's needed: hostdiag, MAIN JUMP, [PlateFix], and the update rate and per-frame cost every 30 seconds.
  • Every experimental API gets a log line written before its first call: if the game crashes, the last line is the culprit.

6. Build and deploy

  • tools/build_hive_lord.py produces a zip Arsenal can import (fixed GUID, one patch per option).
  • tools/deploy_hive_lord.sh only overwrites slots that carry our addon marker, and refuses to deploy while the game is running.
